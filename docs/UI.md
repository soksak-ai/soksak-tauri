# UI 정렬 헌법 — 밴드·박스·구분선 규칙

"자유로우면서 정확하게": 테마는 크기를 자유롭게 정하되, 1px 어긋남은 구조적으로
불가능해야 한다. 이 규칙들은 vitest 게이트(`src/ui/cssContract.test.ts`)가 기계로
강제한다 — 기준을 통과 못 한다고 기준을 약화하는 것은 배신이다(기준 자체가 틀렸으면
문제 제기 후 정정).

## R1. 밴드 패딩 계약

수평 밴드(탭 스트립)의 상하 여백은 **스트립의 `padding-block` 변수만이 소유**하고,
항목(필·버튼·컨트롤)은 **stretch 로 안을 가득 채운다**:

- 뷰 탭 스트립: `--tab-pad` → `.view-tabs` (헤더 33 − 선 1 = 내부 32, 기본 4 → 칩 24)
- 워크스페이스 탭: `--ws-pad` → `.tabs`(타이틀바, 슬롯 36px)·`.content-tabs`
  (37px − 선 1 = 36) — 같은 변수 하나가 `.tab` ≡ `.ctab` 높이를 보장 (기본 5 → 26)

항목 높이 = 밴드 내부 − 패딩×2 가 **유도값**이므로:
- 형제 박스는 정의상 같은 높이·같은 축 — 1px 어긋남 구조적 불가.
- 패딩이 정수면 항목 y 도 항상 정수 — **절반픽셀 센터링 불가**. (높이 변수
  모델은 스트립·항목 높이를 따로 정해 홀짝이 어긋나면 0.5px 에 얹혔다 — 그래서
  폐기. 예: 칩 28 을 내부 37 에 센터 → y=48.5, 상하가 다르게 안티앨리어싱.)

테마(`data-tab-shape`)는 `:root[...] { --ws-pad: 4px }` 처럼 **패딩 변수로만**
크기를 자유 설정한다. 항목 셀렉터의 `height:` 지정은 **금지**(auto 제외) —
게이트가 빌드 실패시킨다. 예외는 가로 밴드가 아닌 곳뿐: `.project-rail`(정사각
칩), `.content-tabs.vertical`(세로 리스트).

**홀짝 규칙**: 밴드 내부 높이는 **짝수**로 잡는다(타이틀바 45−선1=44, 크롬 행
37−선1=36, 그룹 헤더 33−선1=32). 칩(짝수 패딩 차감 후)도 짝수가 되고, 칩 안의
짝수 콘텐츠(아이콘 12/14/16, 닫기 박스 16)까지 정수 센터링된다 — 모든 층위에서
절반픽셀이 사라진다.

## R1a. 크롬 행 계약

수평으로 **이웃한 밴드들**(좌측 헤더 `.ft-header` · 스페이스 탭 `.content-tabs` ·
우측 헤더 `.plugin-side-head` · 좌측 호스트 탭 `.left-host-tabs`)은 한 행이다 —
높이가 1px 만 달라도 구분선이 어긋난다. 높이는 파일 끝의 **규칙 하나**
(`--chrome-row-h`, 37px)만이 소유한다. 개별 블록에 height 지정 금지.

## R2. 정렬은 flex 가 소유

밴드는 `display:flex; align-items:center` 로 자식을 중앙 정렬한다. 위치 보정
(absolute + 음수 오프셋, margin 산수, translateY 미세조정)으로 "맞춰 보이게"
만드는 것은 금지. (이력: `.tab-close` 의 `top:-7px; scale(0.6)` 배지 핵 제거)

## R3. 구분선은 경계이지 여백이 아니다

밴드의 구분선은 `border`(레이아웃 점유)로 긋는다. 시각 대칭의 기준은
"위 여백 = 선 위까지의 아래 여백"이며, border 모델이 이를 자연스럽게 만족한다.
밴드 높이 산식: `패딩 + 항목 + 패딩 + 선(1px)` — 모든 항이 정수다
(예: `.content-tabs` 37 = 5 + 26 + 5 + 1).

## R3a. 테마는 변수이지 CSS 가 아니다

테마가 임의 CSS/SCSS 를 덮어쓰게 하지 않는다: 임의 CSS 는 R1 의 구조 보증을
테마마다 다시 무너뜨리고, 앱 구조
리팩토링 때마다 모든 외부 테마가 조용히 깨진다(전방 호환 붕괴). 테마의 표현
자유는 **승인된 변수 슬롯**(색 토큰 + 구조 노브: `--tab-pad`/`--ws-pad`/radius
류)으로 제공한다 — 노브가 부족하면 슬롯을 추가하는 것이 정도(正道)다.

## R4. 좌표 산수는 CSS 단일 규칙이 소유

JSX 에서 `calc(...)` 문자열을 조립해 인라인으로 흩뿌리는 것 금지. 위치가 필요한
레이어(GroupArea 셀/슬롯/프레임)는 **변수 4개(--l/--t/--w/--h)** 만 넘기고,
산수는 App.css 의 규칙 하나가 가진다. 치수 상수(--header-h/--status-h/--pane-inset)
는 TS 단일 소스에서 1회 주입.

위치 지정이 정당한 경우는 명시된 사유가 있을 때뿐이다:
영속 본문 슬롯(세션 보존), 분할 디바이더(경계 그 자체), 드롭 인디케이터(오버레이).

## R5. 정렬 주장은 수치로 검증한다

"맞아 보인다"는 근거가 아니다. `sok ui.measure '{"address":"..."}'` 로 rect 를 찍어 형제 박스의
y/h 일치와 여백 대칭을 숫자로 확인한 뒤에만 완료를 선언한다. 주소는 §A6 의 노출 노드(`sok ui.tree`)에서
얻는다 — 임의 selector 가 아니다(노출 안 된 요소는 측정 불가).

## A6. DOM 접근은 구조적 주소 — 임의 selector 금지

DOM 요소는 임의 CSS selector(취약·불명확)가 아니라 **구조적 path 주소**로만 접근한다. 주소 문법의 단일
진실은 `src/commands/address.ts`:

```
호스트 뷰:   win/<label>/proj/<root|alias>/<region>/pane/<idx|active>/view/<pluginId.viewId>/inst/<viewId>/node/<nodePath>
호스트 크롬:  win/<label>/proj/<root|alias>/chrome/<chromePath>
region ∈ { left | content | right }
```

`content` 는 여기서 **레이아웃 region 이름**(패널 트리를 담는 중앙 화면 영역)이지,
워크스페이스 탭(스페이스) 개념이 아니다 — 두 층이 같은 단어를 쓰던 시절의 잔재를
R1a 의 "스페이스 탭" 표기로 이미 분리했다(주소 트리의 `tab/space/N` 도 동일 구분).

### 공리 A1 — 유일성

한 창에서 노출된 두 노드는 같은 주소를 가질 수 없다. 주소가 유일하지 않으면 측정도 클릭도
어디로 가는지 알 수 없고, 그 상태에서 통과한 검증은 아무것도 증명하지 못한다.

유일성을 깨는 축이 둘 있고, 문법이 각각에 자리를 준다.

- **같은 뷰키의 여러 인스턴스** — 브라우저 탭 여러 개처럼 같은 `pluginId.viewId` 가 한 영역에
  여러 번 마운트된다. `inst/<viewId>` 가 가른다.
- **프로젝트 평면 전부 마운트** — 세션 유지를 위해 비활성 프로젝트도 화면 밖에 파킹된 채 살아
  있으므로 그 안의 크롬 노드가 프로젝트마다 한 벌씩 산다. 크롬 경로 앞의 `proj/<id>` 가 가른다.

생략 = 활성(win=현재 창, proj=활성 프로젝트, pane=활성 pane, inst=유일 인스턴스). `ui.tree` 는
언제나 정본(생략 없는) 주소를 답하고, 생략형은 활성 대상의 별칭으로만 풀린다.

### 공리 A2 — 무추측

주소는 정확히 하나로 풀린다. 0개면 `NOT_EXPOSED`, 둘 이상이면 `AMBIGUOUS`. **어느 하나를 고르지
않는다.** 예전에는 같은 주소가 여러 요소에 붙는 것을 전제하고 "보이는 것"을 골랐는데, 그 추측은
둘 다 보이는 순간 무너진다 — 실측(2026-07-26): 패널 6개가 전부 `tab/view/0` 을 써서 클릭이 어느
패널로 갈지 알 수 없었고, 노출 노드 779개 중 85개가 주소를 공유하고 있었다. 주소가 유일하지
않다는 것은 주소를 만드는 쪽의 결함이지 고르기로 덮을 일이 아니다.

### 정정 — "카운터 id 금지"의 범위

이 문서는 세그먼트에 카운터 id 를 금지했다. 그 조항의 근거는 재실행 간 값이 달라진다는 것이었고,
그래서 인스턴스 식별에 **위치 인덱스**를 썼다. 그것이 틀렸다: 위치는 탭을 재배열하는 것만으로
바뀌므로 카운터 id 보다 **덜** 안정적이고, 같은 pane 안의 두 인스턴스를 구별하지도 못한다.

조항을 좁힌다 — 금지 대상은 **위치를 식별에 쓰는 것**이고, 인스턴스 식별에는 인스턴스 id 를 쓴다
(`layout/slot/<viewId>` 가 이미 그렇게 하고 있었다). 세션 간 값이 달라지는 성질은 남지만, 주소는
`ui.tree` 로 발견해 쓰는 것이지 소스에 적어 두는 것이 아니다. 세션을 넘어 안정적이어야 하는 축은
root/alias·region·qualifiedViewId·노드path 이고, 그것들은 그대로다.

멱등(같은 구조면 같은 주소)·중복0(계층 유일)·규칙(구조=규칙).

요소 노출은 **명시**다: `data-node="<nodePath>"` 속성을 부여한 요소만 주소 트리에 나타난다. 플러그인은
`contributes.nodes` 로 노드 종류를 선언(동의 화면 표기) 후 `data-node` 로 인스턴스 부여(동적 목록은
`<id>/<안정키>`). 호스트 크롬은 선언 없이 `data-node`(chrome 경로). 노출 안 된 요소 접근은 `NOT_EXPOSED`.

명령(registry 단일진실): `ui.tree`(노출 주소 트리 + `duplicates`)·`ui.measure(address)`(rect/style)·
`ui.snapshot.dom`(한 순간에 전부 측정)·`ui.input.click(address)`(클릭, danger:inject).
`data-pane-id`/`data-group-id`(네이티브 마우스 판정)는 직교한 코어 계약 — 혼동 금지.

**`ui.verify` — 창이 지금 성립하는가.** 위 공리를 포함한 구조 불변식을 앱이 스스로 점검해 이름별로
답한다: `address.unique`(A1)·`rail.settled`(여정 뒤 빠지는 레일이 남지 않는다 — 남으면 사이드바가 두
벌로 보인다)·`slot.sized`(보이는 슬롯의 크기가 0 이 아니다 — 0 이면 그 패널은 빈 화면이다)·
`motion.paired`(화면이 쓰는 시간과 위상이 닫히는 시간이 같다). 판정 기준은 스크립트가 아니라 앱
안에 있고, e2e 게이트(`scripts/e2e/ui-verify.mjs`)는 이 명령을 부르기만 한다 — 기준이 게이트마다
갈라지지 않는다.

**paneId 역참조 앵커 (대칭성 계약).** 코어가 플러그인에 발급하는 paneId(= 콘텐츠 뷰 인스턴스 id —
`command.started` 이벤트·`app.ui.statusBarItem({paneId})` 가 발급)는 DOM 에서 역참조 가능해야 한다. 콘텐츠
뷰 호스트(`PluginViewHost`)는 `.plugin-view-container` 에 `data-pane-id="<viewId>"` 앵커를 노출한다 — 단일
진실은 `src/plugins/viewHostAnchors.ts`. `ui:overlay:pane` 플러그인은 이 앵커로 host 를 찾아
(`[data-pane-id="<paneId>"]`) 그 위에 오버레이를 마운트한다. statusBarItem 을 paneId 로 붙일 수 있으면
오버레이도 paneId 로 붙을 수 있어야 한다 — 비대칭은 계약 위반. 사이드바 호스트의 paneId 는 '추종 대상
터미널'이지 자기 인스턴스 id 가 아니므로 앵커를 안 단다(혼동 금지). [회귀] `942ae86`(내장 터미널 →
플러그인) 에서 코어 터미널 뷰가 박던 이 앵커가 통합 호스트로 이전되지 못해 누락 → paneId 로 host 를 찾는
claude-gui 오버레이가 안 열렸다. `viewHostAnchors.test.ts` 가 재발을 차단한다.

## A6a. UI 변경 검증은 두 경로 — 둘 다 명시한다

살아있는 앱에서 UI 변경을 검증하는 길은 둘이고, 대상에 따라 고른다:

1. **DOM 노출 + 클릭**(A6): 요소에 `data-node` 를 달아 `ui.tree` 에 노출하고 `ui.input.click(address)` 로
   실제 클릭을 주입한다. 사람 조작을 그대로 흉내내는 E2E 경로. **함정**: `ui.input.click` 은 주소가 가리키는
   요소에 이벤트를 디스패치할 뿐이라, `data-node` 가 **실제 상호작용 요소**(버튼)에 얹혀야 발화한다. 컴포넌트
   라이브러리에 따라 임의 `data-*` 를 상호작용 요소가 아닌 곳(접근성 라벨 등)으로 라우팅하거나(예: astryx
   Selector), 아예 `...rest` 를 안 뿌리기도 한다(예: astryx SegmentedControlItem). 클릭이 무반응이면 추측 말고
   `ui.measure(address)` 로 그 주소의 rect 가 진짜 상호작용 컨트롤인지부터 확인한다.

2. **커맨드 재현 + 캡처**: 대상 동작이 registry 명령 뒤에 있으면(플러그인 동작은 대개 그렇다), UI 요소를
   마우스로 클릭하는 대신 **그 요소가 내부에서 부르는 그 명령을 `sok`(또는 MCP)로 직접 실행**하고
   `window.snapshot` 으로 결과를 눈으로 확인한다. 예: 브라우저 패널에서 "Login" 템플릿을 클릭하는 대신
   `sok plugin.<id>.template.apply '{"id":"pages/login"}'` 를 실행한 뒤 `sok window.snapshot '{"path":…}'`
   로 캔버스가 실제 바뀌었는지 캡처해 본다. 버튼의 onClick 이 부르는 바로 그 명령을 쳐서 버그를 재현하고
   고침을 캡처로 확정한다 — DOM 노출이 없거나(위 함정) 컴포넌트가 클릭을 안 넘겨도 동작하며, 명령이 단일
   진실이라 사람 클릭과 같은 경로를 지난다.

원칙: 완료 주장 전에 **둘 중 하나로 실제 앱에서 캡처/실측**한다(격리·프록시 테스트 통과 ≠ 실앱 정확). 명령 뒤
동작은 (2)가 빠르고 확실하다; 순수 UI 상호작용(팝오버 열림·드래그 등)은 (1)이 필요하다.

# B. 보더 소유권 헌법 — 어느 박스가 어느 변을 긋는가

1px 어긋남·누락 선의 근본 원인은 소유권 부재다. 모든 경계선은 **소유자가 정확히
하나**다. 기계 진실은 `src/ui/borderContract.ts` 의 계약 테이블이며, 런타임
검증기 `sok ui.validate` 가 살아있는 DOM 에서 위반을 적발하고(`ui.expect` 는
지정 DOM 의 기대 변을 알려준다), 정적 게이트(`cssContract.test.ts`)가 위반
색상의 유입을 막는다. red→green: 검증기가 먼저 위반을 적발한 뒤에만 고친다.

## B1. 외곽 전속

패널 외곽 4변은 프레임(`.egroup-frame`, 오버레이 z:5) 전속 소유. 내부 요소는
외곽 변에 보더를 긋지 않는다. 표시 여부는 pane 스타일 토큰의 권한(소유≠표시).

## B2. 본문 무보더

본문(터미널/에디터/웹뷰 슬롯)은 보더를 소유하지 않는다 — 불투명 콘텐츠가 자기
보더를 가리는 구조 제약(단일 프레임의 교훈). 본문 인접 경계는 **크롬 밴드가
본문 쪽 변으로 소유**: 헤더류=bottom, 푸터류=top, 좌측 크롬=right, 우측 크롬=left.

## B3. 크롬↔크롬

두 크롬이 만나면 **중심(본문)에서 먼 쪽**이 소유(타이틀바 bottom, 레일 right).

## B4. 색은 토큰 둘뿐

구조선 = `var(--bd)`(앱 크롬·외곽·떠 있는 표면) 또는 `var(--bd-soft)`(패널 내부선,
`color-mix` 파생 — 테마 슬롯 추가 없음). 강조는 `--accbg`. **보더 선언에 직색
(rgba/hex) 금지** — 정적 게이트가 빌드 실패시킨다.

## B5. 프레임 예산

프레임은 오버레이이므로 외곽 접변 요소가 그 변의 1px 을 자기 예산으로 지불한다:
DOM 크롬 밴드는 패딩으로(card/floating). 네이티브 child webview 의 1px 예산은
레이어 원칙(L, 아래)으로 소멸 — DOM 이 webview 위에 그려지므로 프레임 보더는
항상 보인다. 홀-네이티브 정렬의 정수 스냅(소수 rect 금지)만 유지한다.

# L. 레이어 원칙 — DOM 이 항상 최상위다

네이티브 child webview(브라우저 패널)는 OS 뷰 계층에서 메인 webview 의 DOM 과
z-순서를 다툰다. Tauri 의 기본(add_child = 최상위)을 따르면 모든 DOM 오버레이
(모달/메뉴/드롭 인디케이터/포커스 표시)가 webview 아래 깔린다 — 과거에는 이를
"오버레이 동안 브라우저 숨김(suppress)"으로 우회했다. 현재 구조는 역전이다
(`src-tauri/src/browser.rs` 머리말, mod layer):

1. **z-순서 역전**: child webview 는 생성 직후 메인 webview "아래"로 내린다.
2. **투명 홀**: 메인 webview 는 자체 배경을 칠하지 않고(drawsBackground=false),
   루트 CSS 체인은 투명, 표면은 각자 불투명 배경을 소유한다. 브라우저 슬롯
   (`.bv-area`)만 투명 = 홀 — 아래 webview 가 비친다. 미도장 영역의 색은
   네이티브 창 배경(`window_set_background`, 테마 엔진이 bg 와 동기)이 칠한다.
3. **hitTest 위임**: 홀 안 마우스는 네이티브 hitTest 가 아래 webview 로 위임
   한다. 홀의 단일 진실 = "보이는 child webview 의 frame" 그 자체(레지스트리
   없음). 오버레이가 떠 있는 동안(`useOverlayActive` 카운터)은 위임을 차단해
   "바깥 클릭=닫기"가 성립한다 — 브라우저는 보이되 비활성(모달의 본래 의미).

따름정리: ① 모든 DOM 레이어는 브라우저 위에 그려진다 — 숨김(suppress) 금지.
② 루트/조상 체인에 불투명 배경을 되돌리면 홀이 막힌다(App.css 머리말). ③ 활성
뷰가 브라우저인 셀은 본문 영역에 배경을 칠하지 않는다(`.cell-hole`). ④ 네이티브
클래스 정체성은 절대 바꾸지 않는다 — isa-swizzle 은 AppKit design-property
조회(NSDP)에서 SIGABRT(실측: select 팝업 크래시). 메서드 스위즐만 허용.

## B6. 경계 도구는 선을 소유하지 않는다

리사이저/드래그 핸들은 레이아웃 폭 0 오버레이 — 선은 B2/B3 소유자가 긋는다.
**유일한 예외**: 불투명 콘텐츠 사이 seam(터미널 pane 분할 등)은 보더를 들 DOM
소유자가 없으므로, `divider:"solid"` 테마에서 경계 도구가 1px 중앙선을 "표시"
한다(소유 위임). `"overlay"` 에선 휴면 완전 투명(hover 강조만).

## B7. 행 정렬 계약

텍스트+아이콘이 섞이는 행은 컨테이너가 `flex; align-items:center` 를 소유한다 —
아이콘을 베이스라인 플로우에 얹는 것 금지. 세로 중앙 판정은 박스가 아니라
**가시 픽셀**(보더/오버레이 차감 후) 기준(R5 의 수치 검증으로).

## B8. 계약 전수성 — 스펙이 모르는 경계면은 스펙이 못 잡는다

검증기는 등재된 표면만 본다. 그래서 게이트가 세 방향의 동기화를 강제한다:
1. **CSS→계약**: 구조 보더(`--bd*`)를 긋는 셀렉터는 계약에 등재되거나 "위젯
   윤곽"(폐곡선 — 경계면 아님)으로 명시 분류돼야 한다. 미지의 경계면 = RED.
2. **계약→CSS**: 계약의 토큰 규칙은 CSS 에 대응 선언이 있어야 한다(공허 금지).
3. **상태 전수성**: 조건부(when) 표면은 paneStyle×divider 전 상태 공간을
   빈틈·모순 없이 커버해야 한다 — "존재해야 하는 상태"와 **"존재하면 안 되는
   상태"**(예: flat 의 프레임 무선)를 모두 단언한다.

잔여 갭(새 표면을 만들고 선·계약 둘 다 안 넣은 경우)은 절차로 막는다: 새 크롬
표면 추가 시 `sok ui.expect '{"selector":"..."}'` 가 "규칙 없음"을 보고하면
계약 등재가 선행 의무다.
