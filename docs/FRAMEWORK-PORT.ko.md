# 프레임워크 이식

앱이 도는 데스크톱 프레임워크와 어떻게 분리돼 있는지, 두 번째 프레임워크가 얼마나 드는지. [ARCHITECTURE.ko.md](ARCHITECTURE.ko.md)의 한 면이며, 영문 정본은 [FRAMEWORK-PORT.md](FRAMEWORK-PORT.md)다.

프레임워크는 창·웹뷰 생성, IPC, 네이티브 API, 패키징을 함께 주는 것이다 — 지금은 Tauri. 그것은 **전제가 아니라 어댑터**다.

한때 이것을 "셸"이라 불렀다. 그 말은 이미 로그인 셸(zsh·bash)의 것이고 이 저장소는 PTY·터미널을 핵심으로 다뤄 충돌이 실재한다(`login_shell.rs`·`--login-shell`·`shell_which`). `platform` 도 아니다 — 그것은 OS(macOS·Linux·Windows)다.

## 왜 둘인가

Tauri 를 버리려는 것이 아니다. **둘 다 두려는 것**이고, 이유는 하나가 못 하는 것을 다른 하나가 하기 때문이다.

Tauri 는 OS 웹뷰를 쓴다 — macOS 는 WKWebView, Linux 는 WebKitGTK. 얇고 가볍고 모바일까지 가는 유일한 후보다(`multiplatform-engine-strategy.ko.md` §3). 대신 콘텐츠 표면이 **엔진에 묶인다**: WKWebView 가 제대로 못 그리는 사이트는 앱도 못 그린다. 그것이 Chromium 사이드카를 만든 이유이고, 그 사이드카가 hole-punch·hitTest 스위즐·합성 캡처라는 macOS 전용 하위 시스템을 끌고 왔다.

Electron 은 통째로 Chromium 이다. 콘텐츠 문제가 **정의상** 없다 — 브라우저가 하는 것을 앱도 한다. 대신 무겁고, 모바일이 없고, Rust 를 링크하지 못한다.

그래서 둘은 경쟁자가 아니라 **다른 답을 가진 두 축**이다.

| | Tauri | Electron |
| --- | --- | --- |
| 엔진 | OS 웹뷰(macOS WKWebView · Win WebView2 · Linux WebKitGTK) | Chromium 고정 |
| 콘텐츠 등급 | OS 마다 다름 — macOS·Linux 는 미달 | 항상 충족 |
| Rust 백엔드 | 직접 링크 | 불가 — 소켓으로 말한다(cored) |
| 번들 | 작다 | 크다 |
| 모바일 | iOS/Android 1급 | 없음 |
| 자식 콘텐츠 | 네이티브 자식 웹뷰 | DOM 안 `<webview>` |
| 겹침(모달·인디케이터) | z-순서 역전 + 투명 홀 + hitTest 스위즐 | **z-index** — 문제가 없다 |
| 창 캡처 | 자식까지 OS 컴포지터가 합성 | 페이지 캡처로 충분 |

### 특성이 만드는 해결점

각 축의 어려운 부분이 상대에서 사라진다. 그것이 둘을 함께 두는 실익이다.

| 문제 | Tauri 의 해법 | Electron 에서 |
| --- | --- | --- |
| WKWebView 가 못 그리는 사이트 | Chromium 사이드카로 승격 | **소멸** — 프레임워크가 Chromium |
| 모달을 브라우저 위에 그리기 | 홀 + hitTest 스위즐(macOS 전용) | **소멸** — `<webview>` 가 HTMLElement 라 z-index |
| 픽셀 검증 | 자식까지 합성하는 창 캡처 플러그인 | 페이지 캡처(`capturePage`) |
| Rust 로직 재사용 | 같은 프로세스에 링크 | cored 소켓 — 이름·인자·봉투가 같다 |
| 모바일 | 같은 코드가 간다 | 원격 웹 클라이언트로 붙는다 |

반대로 Electron 이 지는 것도 있다: 번들 무게, 프로세스 수, 그리고 Rust 를 **호출**하려면 소켓 왕복이 붙는다는 것.

측정으로 확인한 것 두 가지(문서 주장이 아니라 실측이다):

- `<webview>` 는 `HTMLElement` 를 상속하고(`electron.d.ts`) 그 위에 DOM 을 얹으면 **DOM 이 위에 그려진다** — 오프스크린 캡처로 픽셀을 표본해 확인했다(`scripts/electron/overlay-stacking.test.mjs`). 그래서 홀·스위즐이 필요한 자리가 애초에 생기지 않는다.
- 반대로 `WebContentsView` 로 Tauri 모델을 흉내내면 막힌다. `View` 의 표면에는 뷰 단위 히트 위임이 없고 `setIgnoreMouseEvents` 는 창 단위다(`scripts/electron/layer-model.test.mjs`). **흉내내지 말라는 뜻이지 못 한다는 뜻이 아니다.**

### 플러그인은 프레임워크를 모른다

표면이 요구하는 것은 프레임워크가 아니라 **엔진 등급**이다. 그래서 매니페스트는 벤더가 아니라 필요를 적는다(`packages/plugin-spec/src/engineNeeds.ts`).

```
requiresEngine: "chromium"
  Tauri × macOS    → WKWebView 미달 → 사이드카로 승격
  Tauri × Windows  → WebView2 = Chromium → 승격 no-op
  Electron × 전부  → 프레임워크가 Chromium → 승격 no-op
```

벤더 이름으로 적으면 틀린 답이 나온다. astryx 는 macOS WKWebView 에서 동작하지 않아 Chromium 표면으로 승격된 첫 사례인데, 이것을 "Electron 제외"로 적으면 **Electron 에서 더 잘 도는 것을 숨기게 된다.** Electron 은 요구를 덜 충족하는 것이 아니라 더 충족한다 — 축이 반대다.

충족은 어댑터가 자기 사실로 밝힌다.

| | `chromium` | `nativeChildWebview` |
| --- | --- | --- |
| Tauri | `false` | `true` |
| Electron | `true` | `false` |

Electron 의 `false` 는 못 한다는 뜻이 아니다. 단일 Chromium 세계에서 UI 와 콘텐츠를 같은 컴포지터가 합성하므로 그 장치가 **필요 없다**. 그래서 그 장치를 전제한 표면만 빠지고, 등급만 필요한 표면은 사이드카 없이 그냥 선다.

## 세 축의 어휘

한 축에 세 말이 돌아다니면 어느 뜻인지 매번 물어야 한다. 이 저장소에서는 셋이 각자 다른 것을 가리킨다.

| 말 | 가리키는 것 | 값 |
| --- | --- | --- |
| **framework** | 앱을 호스팅하는 것 — 창·IPC·네이티브 API·패키징 | Tauri · Electron |
| **platform** | 운영체제 | macOS · Linux · Windows |
| **engine** | 웹을 그리는 것 | WKWebView · Chromium · WebKitGTK |
| **shell** | 명령 해석기 | zsh · bash |

`src/platform/` 이 한때 프레임워크 어댑터를 담고 있었다. 안의 모든 것이 "셸"이라 말하는데 폴더만 `platform` 이었으니 정착된 어휘가 아니라 혼자 어긋난 이름이었고, 그 위에 세운 논거는 전부 낡은 자리를 원칙처럼 따르는 것이었다. 지금은 `src/framework/` 다.

## 경계

`src/framework/contract.ts` 가 `AppFramework` 를 선언한다. 프레임워크마다 폴더 하나를 갖고(`src/framework/tauri/`, `src/framework/electron/`) 그 안의 `index.ts` 가 계약을 구현한다. `src/framework/index.ts` 가 활성 어댑터를 해소해 이름 있는 함수로 재수출한다. 그 밖의 모든 파일은 `../framework` 에서만 가져오고 어느 프레임워크가 밑에 있는지 끝내 모른다.

- **쓰는 것만 담는다.** 계약에는 `invoke`·스트림·전역 리슨·현재/라벨 창(논리·물리 두 축, 테마, 드래그드롭)·app·path·dialog·notification·deepLink 가 있다. 앱이 실제로 부르는 것들이다. 쓰지 않는 능력을 미리 선언하면 어댑터마다 흉내 낼 수 없는 빈칸이 생기고, 빈칸은 결국 경계를 우회해 메워진다.
- **벤더의 결함은 어댑터가 흡수한다.** Tauri 의 unlisten 은 이미 해제된 리스너를 다시 해지할 때 promise 를 reject 한다. 계약이 "해지는 멱등"이라 말하므로 어댑터가 삼키고 그 이유를 적어 둔다. 흡수는 어댑터의 몫이지만 정책과 상태는 아니다 — 프레임워크마다 달라지는 정책은 그 자체가 프레임워크 종속이다.
- **게이트가 시행한다.** `src/framework/frameworkSeam.test.ts` 는 `src/framework/` 밖의 어떤 파일이든 프레임워크 벤더를 import 하면 실패한다. 테스트도 같은 규칙 아래 있다: 벤더가 아니라 `../framework` 를 모킹한다. 테스트가 벤더를 알면 프레임워크 교체가 테스트까지 뜯는 일이 된다.

프레임워크를 하나 붙이는 일은 어댑터 파일 하나 + 해소표 한 줄이며, 앱 파일은 한 줄도 바뀌지 않는다.

개발 서버도 프레임워크 정체성의 일부다. `frameworks/dev-endpoints.json` 이 프레임워크별 URL과
포트를 선언하고 Vite와 Electron 호스트가 그 선언을 읽는다. Tauri 설정의 `build.devUrl`은 같은
선언과 테스트로 일치시킨다. 두 제품 프레임워크는 개발 엔드포인트를 공유하지 않는다. 한 서버의
번들을 다른 호스트가 받으면 어댑터 import graph 자체가 바뀌므로 런타임 감지로 보완할 문제가 아니다.

## 스트림 출구

위의 경계는 앱 쪽을 덮는다. 고volume 출력이 프로세스 밖으로 나가는 출구는 또 하나의 경계이고, 네이티브 핸들러를 그 자리에 묶어 둔 것이 그것이다.

네이티브 명령 표면 전수 분류(2026-07-27)의 결론은 병목이 상태 소유권이 아니라는 것이었다 — 상태는 대부분 창 무관이거나 라벨 문자열이 키다. 병목은 웹뷰 IPC 가 스트리밍 출구를 독점한다는 점이다. `tauri::ipc::Channel` 은 호출 웹뷰의 IPC 문맥에서 역직렬화로 만들어지는 핸들이라 `Serialize` 가 아니고, 라벨로 재구성할 수 없고, 프로세스 경계를 못 넘는다. 그 타입이 시그니처에 박혀 있는 한 그 핸들러는 앱 프로세스를 떠날 수 없다 — 라벨만 있으면 옮길 수 있는 7건 중 3건이 오직 이것 때문에 묶여 있었다.

- **계약은 두 줄이다.** `frameworks/tauri/src/stream_sink.rs` 가 `StreamSink::deliver(&self, bytes: Vec<u8>) -> Delivered` 를 선언한다: 배치 하나를 건네고, 소비자가 사라졌으면 그 사실을 값으로 알린다(`Delivered::Gone`). 조용히 버리는 출구는 생산 측을 영원히 읽게 만든다. 같은 파일의 `impl StreamSink for tauri::ipc::Channel<tauri::ipc::InvokeResponseBody>` 가 현 정본 구현이며, 구현은 크로싱마다 하나다.
- **전달 단위 소유자는 더 이상 벤더를 부르지 않는다.** `frameworks/tauri/src/pty_delivery.rs` 의 `spawn_delivery` 는 `S: StreamSink` 로 일반화돼 있고, 두 PTY 백엔드가 그 한 크로싱에서 끝난다 — `frameworks/tauri/src/pty.rs` 의 인프로세스 리더 스레드와 데몬 릴레이 `spawn_via_daemon`. 벤더 타입은 `#[tauri::command]` 진입점(`spawn_terminal`)에만 남는다. 호출자에게서 채널이 도착해 출구로 건네지는 자리다.
- **배압은 계약에 없다.** 워터마크(`soksak_spec_pty::HIGH_WATERMARK` / `LOW_WATERMARK`)와 ack 는 세션의 것이다: 리더 스레드가 미ack 바이트를 세어 상한에서 멈추고, `ack_terminal` 이 빼면서 하한에서 재개한다. 그 회계는 읽은 바이트 기준이라 배치가 언제 나가든 같다. 출구가 배압까지 쥐면 구현마다 정책이 갈라지고, 갈라진 정책은 곧 무한 버퍼다.
- **테스트가 증명이다.** `stream_sink.rs` 는 Tauri 타입이 하나도 없는 출구를 구현한다(`a_sink_needs_no_shell_type`, `a_departed_consumer_is_reported_not_swallowed`). 그것이 컴파일된다는 사실 자체가 "출구는 더 이상 벤더 타입이 아니다"의 진술이다.

지금까지 옮긴 것은 PTY 출력 크로싱이다. 나머지 채널 보유자 — 프로세스 stdout/stderr·종료(`frameworks/tauri/src/process.rs`), 웹소켓 메시지·닫힘(`frameworks/tauri/src/ws.rs`), 사이드카 이벤트(`frameworks/tauri/src/sidecar.rs`) — 는 아직 시그니처에서 벤더를 부르며, 위 규칙이 그대로 적용된다.

## 나머지 세 경계

같은 모양이 되풀이된다. 각각은 프레임워크가 쥐고 있던 사실을 값이나 계약으로 바꾸고, 벤더 타입 없이 그것을 구현하는 테스트가 시행한다 — 그 테스트가 컴파일된다는 사실 자체가 증명이다.

| 계약 | 파일 | 벤더에서 뗀 것 |
| --- | --- | --- |
| `WindowOracle` | `frameworks/tauri/src/window_oracle.rs` | 어느 창이 살아 있는가, 라벨로 배달 |
| `ActivitySink` | `frameworks/tauri/src/activity_sink.rs` | 활동 원장 발행 |
| `Identity` | `frameworks/tauri/src/identity.rs` | 이 실행물이 누구이고 어느 홈을 쓰는가 |

- **`WindowOracle` 은 사실만 말하고 선택은 하지 않는다.** 어느 창을 고를지(폴백 사다리)는 호출자의 것이다. 오라클이 선택까지 쥐면 구현마다 사다리가 갈라지고, 갈라진 사다리는 창마다 다른 라우팅이 된다. 배달은 성공 여부를 값으로 돌린다 — 실패를 삼키면 호출자가 보냈다고 믿고 응답을 영원히 기다린다.
- **`ActivitySink` 는 원장에 한 줄 남기고 싶을 뿐인 함수가 `AppHandle` 을 받고 있었기 때문에 있다.** `activity::publish` 는 관리 상태에서 허브를 꺼내고 창에 emit 하고 영속한다 — 시그니처 하나 뒤에 일이 셋이고, 호출 지점은 22곳이다. 다만 이것이 **풀지 못한 것**을 함께 적는다: 네이티브 표면 전수 적대 감사에서 publish 만 끊으면 풀리는 핸들러는 0개였다. 그것을 만지는 자리는 전부 `AppHandle` 시그니처나 네이티브 객체를 함께 갖는다. 진짜 결속이지만 좋은 지렛대는 아니다 — 두 사실 다 남길 값이 있다.
- **`Identity` 는 홈과 identifier 를 함께 나른다.** 둘을 따로 읽고 있었고(`app_environment` 는 앰비언트를 다섯 번 읽었다), 그러면 어긋난 조합("A 홈인데 B identifier")이 표현 가능해진다 — 그 조합은 어느 identity 에도 없다. `ambient()` 가 경계의 이쪽 끝이다: 전역을 한 번 읽고 그 아래로는 값이 흐른다. `Identity::path` 는 항상 홈 아래에 떨어진다. `Path::join` 은 절대경로를 받으면 베이스를 버리는데, 포함을 두고 거짓말하는 계약은 호출자가 자기 검사를 생략하는 근거가 된다.

감사는 앰비언트 홈을 단일 최대 지렛대로 지목했다: 28개가 닿아 있고 끊으면 15개가 풀린다. 다른 어떤 패턴도 단독으로는 0개를 푼다.

## 코어 크레이트

`crates/soksak-core` 은 프레임워크가 들어 있지 않은 명령 로직을 담는다. 여기 있는 것은 앱 프로세스에서든 cored 에서든 같은 답을 내며, 그 조건은 셋이다: 창·앱 핸들·관리 상태를 만지지 않는다, 프로세스 환경·현재 디렉터리·실행 파일 경로를 읽지 않는다, 자기 컴파일 타깃과 빌드 프로파일을 근거로 삼지 않는다.

셋째가 조용하다. `cfg!(target_os)` 로 답이 갈리는 함수는 자기가 컴파일된 바이너리를 서술하는 것이지 호출자가 물은 것을 답하는 게 아니다. 플랫폼 분기는 인자로 받는다.

**이름은 아닌 것이 아니라 인 것을 말한다.** 이 크레이트가 core 인 이유는 앱도 cored 도 여기 있는 로직을 자기 것으로 부르고 둘 다 이것 없이는 아무 명령도 답하지 못하기 때문이다. 부정("프레임워크에 묶이지 않은")으로 지은 이름은 사물이 아니라 경계를 서술하고, 경계가 움직이는 순간 낡는다.

모듈: `activity`·`identity`·`integrity`·`kv`·`pathx`·`plugin_dir`·`session`·`themes`·`udp`·`unit_dev` — 목록의 선언 자리는 `crates/soksak-core/src/lib.rs` 다. 코어에는 위임만 하고 아무것도 판단하지 않는 `#[tauri::command]` 래퍼가 남는다 — 래퍼의 판단은 cored 프로세스가 잃어버릴 판단이다.

**없는 디렉터리는 빈 목록이고, 못 읽는 디렉터리는 오류다.** `plugin_dir::scan` 과 `themes::scan` 은 둘 다 실패로 다뤘었다. 근거는 "설치된 게 없다"와 "디렉터리를 못 읽었다"가 같은 답이 되면 안 된다는 것이었고 그 근거는 그대로다 — 옮긴 것은 경계뿐이다. 두 모듈의 `read_dir_or_empty` 가 `ErrorKind::NotFound` 만 빈 경우로 가르고, 권한 거부·디렉터리 아님은 사유를 달고 계속 실패한다.

이 구분이 필요한 이유는 홈의 소유가 두 프로세스에서 다르기 때문이다. 앱은 스캔 전에 `create_dir_all` 로 자기 홈 배치를 만들어 두므로 부재를 만날 일이 없다. cored 는 남의 홈을 읽을 뿐이라 그 부작용을 지지 않고 — 읽기 명령이 디스크를 만들지 않는다 — 신선한 홈에서 곧장 부재를 만난다. 거기서 오류를 올리면 한 이름의 명령이 프로세스마다 다른 답을 내고(2026-07-28 라이브 실측: 앱 `[]`, cored `os error 2`), 그것이 바로 코어 크레이트가 막으려던 것이다. 두 테스트가 양쪽을 함께 쥐고 있어 빈 경우를 넓혀 진짜 읽기 실패까지 삼키게 만들 수 없다.

`tests/no_framework.rs` 가 두 겹으로 시행한다: 직접 참조를 잡는 심볼 검사와, 의존성이 끌고 들어온 것을 잡는 `cargo tree` 검사. 금지 심볼마다 그것이 왜 이동을 막는지를 함께 적는다 — 이유 없는 금지는 우회 대상이 된다.

코어에도 게이트가 둘 있다. `crates/soksak-core/src/ambient_gate.rs` 는 환경을 읽는 모든 자리에 두 답을 요구한다 — 왜 이 프로세스의 환경이어야 하는가, 프로세스가 갈리면 무엇이 대신 오는가. 빈 답은 실패이므로 표를 통과 수단으로 쓸 수 없다. 이 게이트는 수동 조사가 놓친 세 자리를 즉시 찾았다. 규칙은 스캔 뿌리를 인자로 받고 `crates/soksak-core/tests/ambient_gate.rs` 가 `frameworks/` 아래를 발견해 전부 먹인다 — 한 프레임워크 이름 밑에 살던 규칙이 이제 양쪽을 함께 판정한다. 로그인 셸을 읽는 자리는 프레임워크마다 하나로 센다(프로세스가 둘이면 각자 한 번씩 읽는 것이 옳다). `frameworks/tauri/src/lib.rs` 의 등록 게이트는 등록된 핸들러가 컴파일되는 모든 플랫폼에 본체를 갖는지 본다 — 컴파일러는 지금 빌드하는 플랫폼만 검사한다.

## 앱 프로세스를 전제하지 않게 된 상태

세 서브시스템을 주입형으로 돌렸다. 셋 다 의미는 그대로고 값이 어디서 오는지만 바뀌었다.

- **볼트(`secrets.rs`)** 에는 조용한 오답 생성기가 있었다. `vault_file()` 이 경로 미주입 시 `home::soksak_home()` 으로 폴백했는데, 그 함수는 `init` 전에도 `~/.soksak` 을 답하므로 폴백이 실패하는 법이 없다. 경로를 잊은 `SecretsState` 는 에러가 아니라 릴리즈 사용자의 볼트를 가리켰다. cored 로 옮기면 그대로 남의 홈에 볼트를 만든다. 폴백을 없애고 미구성은 이름을 달고 실패시킨다 — 미구성은 값이 없는 것이지 기본값이 있는 것이 아니다. 키체인 서비스명도 같은 모양이었다: 틀린 서비스명은 거부가 아니라 다른 기기의 KEK 를 여는 시도로 끝난다. 둘 다 `Identity` 에서 파생한다. 암호 프리미티브와 봉인 포맷은 손대지 않았다.

**부팅은 볼트를 열지 않는다.** setup 끝에 `is_unlocked()` 가 있었다 — "투명 개방 시도"가 OS 키체인에 닿고, 키체인 취득은 동기 모달을 띄울 수 있다. 창 하나 뜨기 전에 프로세스가 사람 손을 기다렸고, 자동 실행은 전부 거기서 멈췄다.

부팅은 열 것이 없다. 봉인된 값을 실제로 필요로 하는 쪽이 키를 잡는다 — 취득을 미룬 것이 아니라 부팅에 그 요구가 없었다. `secrets::boot_wire` 가 경로·`expect_vault`·KEK 출처·고지 채널을 심고 끝낸다.

`secrets-ready` 의 뜻도 날카로워졌다: "부팅이 지났다"가 아니라 "볼트가 방금 열렸다"다. 잠긴 볼트를 준비됐다고 말하면 드레인이 빈손으로 돌아 서비스만 재시작되고, 끝내 안 열리면 이 사건도 없다. `boot_wiring_never_touches_the_keychain` 이 접촉을 센다 — 부팅 후 0, 첫 사용에서 1, 재사용에서 증가 없음.
- **설치자(`unit_installer.rs`)** 는 맨 홈 대신 `Identity` 를 받고, 다섯 트랜잭션 입구가 `&UnitInstallManager` 로 열린다 — `State` 가 필요 없다. 원장의 단일 쓰기자 의미는 그대로다.
- **원장(`activity.rs`)** 은 셋으로 갈렸다: `admit`(적재·seq 부여, 순수) · `fan_out`(창과 소켓 구독자, `WindowOracle` 경유) · `persist`(`Connection` 하나). `publish` 는 시그니처와 반환값을 유지한 채 셋을 얹으므로 호출 지점 22곳의 동작이 그대로다. cored 는 적재만 하고 부채질은 프레임워크에 남긴다.

`WindowOracle` 에 수신자 없는 사건을 위한 `broadcast` 가 붙었다. 기본은 살아 있는 창 전부를 걷고, Tauri 는 한 번의 `emit` 으로 대체한다 — 그 한 번의 배달이 자식 웹뷰까지 닿기 때문에 라벨 순회로 바꾸면 받는 쪽이 조용히 줄어든다. 부분 배달은 성공으로 보고하지 않는다.

## 자식-프로세스 함대

터미널·프로세스·데몬·웹소켓·서비스는 가장 큰 이동 가능 묶음이었다 — 창 의존이 라벨 문자열뿐인 핸들러 32개. 이들을 묶어 두던 것은 `tauri::ipc::Channel` 이었고, 스트림 출구 계약이 이미 그것을 풀었다.

- **정체성은 인자가 아니라 필드다.** `Link` 는 control 연결을 캐시하고, 그 연결은 이미 어느 홈의 소켓·토큰으로 맺어진 것이다. 홈을 호출 인자로 받으면 "캐시된 연결은 A 홈, 이번 인자는 B 홈"이 표현 가능해지고 재연결이 그때 B 로 붙는다. 매니저가 정체성을 소유하는 이유는 정체성이 그 존재의 조건이지 호출의 파라미터가 아니기 때문이다.
- **생성이 빌더 체인에서 `setup` 안으로 옮겨졌다.** `home::init` 은 `setup` 최상단에서 도는데 빌더 체인은 그 전이다 — 거기서 정체성을 읽으면 `home.rs` 폴백인 `~/.soksak` 이 잡히고, dev 빌드가 릴리즈 홈의 데몬을 겨눈다.
- **종료는 바이트가 아니다.** `on_exit` 이 나르는 것은 수 하나이고 `Channel<i32>` 는 그것을 JSON 수로 직렬화한다. 바이트 계약에 억지로 끼우면 소비자가 받는 페이로드 형태가 달라지는데, 그것은 구조 이전의 옷을 입은 동작 변경이다. `ExitSink` 는 `StreamSink` 옆에 같은 모양으로(사라짐을 값으로) 서되 타입만 다르다.
- **중개 신원이 프레임워크 어댑터를 떠났다.** 그것은 코어가 찍는 스탬프이지 서비스의 자기신고가 아니다. 어댑터 안에 있으면 두 번째 프레임워크가 다르게 찍고, 다르게 찍힌 origin 은 낭독 후보 제외를 뚫는다.

결속 하나는 의도적으로 남겼다. `pty.rs` 의 `activity::publish` 여덟 자리 중 일곱은 같은 함수가 핸들을 `state::<PtyManager>` / `state::<SecretsState>` 조회에도 쓴다. 거기 남은 `AppHandle` 을 쥐고 있는 것은 발행이 아니라 그 조회이고, 그것을 풀려면 managed state 소유권을 바꿔야 한다 — 동작 변경이므로 별도 회차의 몫이다.

## 잔여 상태

마지막 이동 가능 묶음: 스케줄·명령 브리지·클립보드·watcher·레지스트리 셋.

- **다섯 번째 계약.** `CommandDispatch`(`frameworks/tauri/src/command_dispatch.rs`)는 registry 명령 하나를 부르고 답을 받는 능력이다. 스케줄러가 원하는 것은 그것뿐인데 그 능력을 제공하는 세 함수가 전부 `&AppHandle` 을 받아서, 발화 코드도 하나를 쥐고 있었다. 기존 네 계약 어디에도 맞지 않았다 — 억지로 끼우면 그 계약이 겸업하게 되고, 그것이 `ExitSink` 가 `StreamSink` 안이 아니라 옆에 선 이유와 같다.
- **중개 계약은 창을 모른다.** 명령이 어느 창으로 갈지는 `ipc.rs` 의 폴백 사다리가 계속 소유하고, 호출자는 명령과 답만 안다. 여기에 라우팅을 넣으면 구현마다 사다리가 갈라진다.
- **배달이 한 점으로 모였다.** 두 `emit_to` 자리가 각각 seq 발급·pending 등록·배달을 복제하고 있었다. 이제 한 함수다 — 중복 제거가 아니라 "배달이 실패하면 대기 자리를 되돌린다"가 한 곳에서 강제되기 때문이다. 남은 자리는 오지 않을 답을 기다린다.
- **클립보드가 마지막 필드 핸들을 내놓았다.** `ClipboardState` 는 `AppHandle` 을 필드로 직접 쥔 유일한 managed 상태였고 용도는 emit 이었다. watcher 의 `init`/`init_with` 주입이 이미 그 모양이었다. `lib.rs` 는 바뀌지 않았다 — `init` 은 시그니처를 유지하고 몸통만 옮겼다.
- **유령 필터가 오라클에게 묻는다.** `project_owners` 는 `get_window(label).is_some()` 으로 죽은 점유를 걸렀다. 필요한 것은 핸들이 아니라 "이 라벨이 살아 있는가"이고, 계약이 이미 그 답을 갖고 있다.

의도적으로 남긴 것이 둘이다. `native_reload` 는 웹뷰 핸들을 그대로 쥔다 — 리로드는 창 사실도 배달도 아니고, 두 줄 오라클에 접으면 오라클이 웹뷰 수명까지 쥐게 된다. `state::<T>()` 조회도 그대로다 — 전환은 `lib.rs` 의 `manage` 와 모든 호출자를 한 번에 바꾸는 일이고 `service.rs` 가 같은 판정을 이미 기록했다. 상태 전달 방식이 둘로 갈라지는 것이 그 결속보다 나쁘다.

## cored 프로세스

`crates/soksak-cored` 는 창도 웹뷰도 앱 핸들도 없는 프로세스다. 유닉스 소켓을 열고 `soksak-core` 로직으로 명령에 답한다. 독립 cored 의 선례인 `soksak-ptyd` 를 따르되 두 곳이 의도적으로 다르다.

**이름이 곧 정체다: 데몬으로 도는 core.** 이것이 백엔드이고, 백엔드는 하나다.

```
sok CLI      ──소켓──┐
Tauri        ──소켓──┼──>  soksak-cored   (= 소켓을 입은 soksak-core)
Electron     ──소켓──┘
헤드리스      = 프레임워크 없이 cored 만
```

이것은 앞선 규칙을 뒤집은 것이고, 뒤집은 것이 요점이다. 그 규칙은 이렇게 적혀 있었다: *"다리가 아니다 — Tauri 는 이 프로세스와 말하지 않는다. 그것은 `soksak-core` 를 직접 링크해 자기 프로세스 안에서 함수로 부르고, 그 사이에 소켓을 두면 자기 자신에게 왕복하는 셈이다."* 그 말은 **앱이 한 번에 하나만 돌 때** 전부 참이었다. 그 전제가 사라졌다. 이제 두 프레임워크가 한 홈 위에서 돌고, 그 순간 "앱도 백엔드다"는 더는 공짜가 아니다.

- 저장소는 설계상 단일 쓰기다(`soksak_core::store_lock`). 한 홈에 백엔드 프로세스가 둘이면 쓰기자가 둘이고, SQLite 는 그것을 막지 않는다 — 직렬화할 뿐이다. 그 잠금이 시끄럽게 만들려던 바로 그 조용한 경우다.
- 같은 중복이 일곱 번 더 나타난다. 한 원장 행에 쓰는 `seq` 할당자 둘, 자기 프로세스를 못 벗어나는 `data-change` 통지, 프로세스 메모리에 든 프로젝트 점유 장부(프레임워크 경계에서 P6 가 깨진다), 그리고 설치 스테이징·서비스 원장·백업 링의 고정 임시 이름.

그것은 일곱 문제가 아니다. 한 문제를 일곱 번 본 것이다 — **규칙의 구현이 두 벌이었다.** 실측: cored 는 `soksak_core` 를 68회 부르는 얇은 배선이고, Tauri 앱의 `data/` 는 3132줄에 공용 크레이트 호출이 통틀어 14회다. 하나는 백엔드의 이음매이고 다른 하나는 두 번째 사본이다.

그래서 선은 **용도**로 긋는다. 그 선은 이미 코드에 있다 — `crates/soksak-cored/tests/no_framework.rs` 가 `tauri`·`wry`·`tao`·`objc2`·`block2`·`libloading`·`clipboard-rs`·`x11rb`·`windows-sys`·`tokio`·`interprocess`·`portable-pty` 를 이름으로 막는다.

| | 소유 |
| --- | --- |
| **코어**(cored) | 규칙·저장소·원장·파일·프로세스 — cored 는 이미 스폰한다(`registry.rs`, ptyd 의 `ensure_daemon`) |
| **프론트**(프레임워크) | 창·웹뷰·OS 표면·네이티브 크레이트 — 그리고 **몸이 창인** 명령의 배달을 받는 호스트 |

코어 하나에 프론트 둘은 줄여야 할 비용이 아니다. 그 이음매를 습관이 아니라 계약으로 세워 두는 것이 그것이다. 둘은 서로의 오라클이고, 이 이식이 찾아낸 것 상당수가 Tauri 가 조용히 하던 일을 Electron 이 못 했기 때문에 드러났다.

`soksak-cored` 는 바이너리이면서 **라이브러리**다. 그래서 "백엔드"는 **역할**이다: `Ctx` 를 세우고 쓰기 잠금을 잡고 `wire::answer` 를 서빙하는 프로세스. 링크만 하고 `Ctx` 를 안 세우면 부를 것이 없고, 자기 `Ctx` 를 세우면 그것이 두 번째 쓰기자다. cored 가 그 역할을 지는 것은 능력이 아니라 **결정성** 때문이다 — 부팅마다 호스트를 고르면 위상이 기동 순서에 딸린다.

- **자기 정체성을 파생하지 않는다.** `ptyd` 는 `SOKSAK_HOME` 을 읽어 경로를 파생하지만, cored 는 `--socket`·`--home`·`--identifier` 를 인자로 받고 없으면 기본값을 고르지 않고 이름을 달고 실패한다. 자기 정체성을 추측하는 cored 는 홈이 갈리는 순간 다른 곳에 붙고, 그것도 조용히 한다.
- **`--data-dir` 이 선택인 이유는 이동을 띄운 쪽만 알기 때문이다.** 저장소는 보통 홈에서 파생되지만 앱이 debug 빌드에서 그 자리를 옮긴다. 옮긴 쪽만 아는 사실이므로 cored 를 띄우는 쪽이 넘긴다. cored 가 규칙만 보고 파생하면 앱과 다른 파일을 열고, 그 오답은 오류가 아니라 빈 결과로 도착한다.
- **이름과 인자는 앱의 것이다.** 봉투는 소켓 계약을 따르고 `data` 에는 앱의 `invoke` 가 돌려주는 값이 그대로 실린다. 이름을 번역해야 하는 프레임워크는 새 드리프트 면을 만든다 — 같은 질문으로 같은 답을 받는 것이 요점이다.
- **표가 스스로 답한다.** `cored.commands` 는 `{ commands, unserved }` 를 돌려준다 — 무엇을 서빙하는지(인자마다 이름·타입·필수 여부)와 무엇을 서빙하지 않는지(`blockedBy` 사유). `UNKNOWN_COMMAND` 한 줄만 받는 프레임워크 저자는 "아직 안 옮겼다"와 "여기서는 못 한다"를 구분하지 못해 막힌 것을 다시 조사하거나, 더 나쁘게는 조사 없이 흉내를 낸다.

각 핸들러는 `soksak-core` 호출 한 줄이다. 판단은 cored 에 살지 않는다 — 살면 앱 경로와 cored 경로가 다른 답을 낼 수 있고 그 차이는 조용하다. 로직의 소유자가 하나이므로 두 프로세스는 사본이 아니라 구조적으로 일치한다.

**저장소는 프레임워크가 아니다.** `rusqlite` 는 `soksak-core` 에서 금지이고 cored 에서 허용이다. 금지 목록이 막는 것은 창·웹뷰·네이티브 런타임이며, 데이터베이스는 창을 열지도 앱 핸들을 쥐지도 않고 어느 프로세스에서 열든 같은 파일을 같은 답으로 읽는다. 다만 저장소를 아는 로직은 파일이 있는 곳에서만 돌게 되고 그 전제가 바로 이 분리가 없애려던 것이다 — 그래서 `KvRows`·`KvWrite` 계약과 질의문 자체(`SELECT_SQL`·`UPSERT_SQL`)가 코어에 남고, cored 에는 연결만 산다. 두 프로세스가 각자 SQL 을 적으면 갈라지고, 갈라진 질의는 오류가 아니라 **다른 답**이다.

**쓰려면 혼자임을 증명해야 한다.** 단일 쓰기자는 지금까지 코드 배치에 대한 논증이었다: 앱 프로세스에 커넥션이 하나뿐이고 `Mutex` 가 직렬화하므로 `unchecked_transaction` 이 안전하다. 그 논증은 프로세스가 하나일 때만 성립한다. 두 번째가 같은 파일을 열어도 SQLite 는 막지 않고 직렬화해 줄 뿐이라, 전제가 조용히 사라진다.

그래서 전제를 값으로 만든다. `soksak_core::store_lock` 이 저장소 옆에 권고 잠금(`soksak.db.writelock`)을 걸고, 못 잡은 프로세스는 쓰지 않는다. 커널이 파일 서술자에 거는 잠금이라 프로세스가 죽으면 풀린다 — PID 파일 방식이 늘 필요로 하는 유령 잠금 회수가 원리적으로 없다. 읽기는 잠그지 않는다: WAL 은 읽기 동시·쓰기 단일이고 이 잠금이 지키는 것은 쓰기뿐이다. **못 쓰는 것과 못 보는 것은 다른 사실이다.**

cored 는 부팅에서 한 번 잠금을 시도한다. 잡았으면 `data_kv_set` 을 서빙하고, 못 잡았으면 그 명령을 이름을 달고 거절한다 — 거절이 저장소를 지목한다. 조용한 쓰기가 이 잠금이 막으려는 바로 그 일이다.

**잠금 밖에 있는 쓰기가 하나 있다 — 활동 원장이다.** `activity_publish` 는 이 프로세스가 쓰기를 소유하든 아니든 행을 남긴다(`crates/soksak-cored/src/ledger.rs` 의 `persist`). 실수가 아니라 선택이다. 적재만 하고 안 남기던 것이 이 원장의 옛 모습이었고, 그때의 실측은 **publish 24회 성공에 `records` 0행**이었다 — 답은 전부 성공이었고 부재는 다음 부팅에서 "아무 일도 없었던 것"으로만 드러났다. 이 경로에 잠금 게이트를 달면 그 침묵이 글자 그대로 돌아온다. 반대로 시끄럽게 거절하면, 프레임워크가 지는 부채질 절반이 읽을 수는 있는 저장소 위에서 실패한다. 그래서 대가는 감추지 않고 적는다: 앱이 잠금을 쥔 홈에서 cored 도 함께 돌면 두 프로세스가 `records` 에 쓴다. `crates/soksak-cored/tests/writes_outside_the_lock.rs` 가 두 쪽을 함께 못 박는다 — 지켜지는 쓰기는 거절되고, 원장 쓰기는 행을 남긴다. 어느 쪽이 움직여도 검사가 빨개진다.

**요구 원장이 가르친 것.** Electron 은 백엔드 호출을 순서대로 기록한다. 빈도로 읽으면 `activity_publish`(28)와 `data_kv_get`(10)이 압도적이지만, **순서로** 읽으면 부팅이 멈추는 곳은 5번(`app_environment`)과 7~14번(`data_kv_get`)이다. 빈도만 보고 먼저 배선한 셋은 42·48·50번째였다 — 서빙은 됐지만 창이 그려지는지와는 무관했다. 빈도는 틀린 일을 고르고, 순서는 막고 있는 일을 고른다.

**인자는 호출자의 것, 상태는 프로세스의 것.** cored 가 서빙하는 명령은 같은 이름의 앱 명령과 **인자 모양이 같아야** 한다. UI 는 누가 답하는지 모른다 — `invoke("app_environment")` 는 앱이 답하든 cored 가 답하든 한 번의 같은 호출이다.

첫 판은 이것을 깼다. "cored 는 자기 정체성을 추측하지 않는다"를 근거로 `identifier`·`home`·`dbPath`·`dir`·`base` 를 매 호출 인자로 요구했는데, 그 이름의 앱 명령들은 **인자를 하나도 받지 않는다**. 그 값들은 호출자가 실어 나르는 것이 아니라 프로세스가 갖는 상태이기 때문이다. 라이브 실측(Electron 부팅, 기록된 호출 168건)에서 서빙한다고 믿은 5개가 전부 `INVALID_PARAMS` 로 거절됐고, 그 거절은 프레임워크 로그 한 줄이라 조용했다.

전제는 옳았고 결론이 틀렸다: **받는 것은 추측하는 것이 아니다.** 앱도 자기 정체성을 추측하지 않는다 — 부팅 때 프레임워크 설정에서 받는다. cored 는 띄운 쪽에서 받는다. 그래서 규칙은 두 줄이다.

- 호출자가 보내는 값은 인자다(`ns`·`key`·`host`·`port`)
- 프로세스가 갖는 값은 부팅 상태다(정체성·홈·저장소 경로)

`frameworks/tauri/src/cored_shape_gate.rs` 가 이것을 시행한다. 앱의 모든 `#[tauri::command]` 시그니처를 읽고, 프레임워크가 주입하는 인자(`State`·`AppHandle`·`Window`·`Channel`)를 뺀 뒤, 이름이 겹치는 명령마다 인자 이름 집합을 서빙 표와 대조한다. 심은 위반 세 가지(인자 추가·누락·개명)가 이 게이트가 통과로 위장하지 않고 실제로 드리프트를 잡는다는 증거다.

소켓 테스트도 같은 교훈을 진다: 이제 픽스처 홈을 지목해 cored 를 띄우므로 인자 없는 명령이 **프로세스 밖에서** 검증된다. 인프로세스 검사는 "선언한 대로 인자를 읽는가"까지만 증명할 수 있고, 선언 자체가 앱과 어긋났다는 사실은 볼 수 없었다.

`activity_publish` 는 서빙한다 — cored 가 적재하고, 남기고, 도장 찍힌 항목을 돌려준다. 갈라지는 것은 부채질뿐이다: 거기엔 창이 필요하고 이 프로세스엔 창이 없으니 그 절반은 프레임워크가 진다. 갈라진 것은 답이지 규칙의 사본이 아니다.

아직 서빙하지 않는 것과 무엇이 막는지는 이름 옆에 함께 적혀 있다(`crates/soksak-cored/src/registry.rs`): `project_owners`(점유 원장이 앱 프로세스 안의 가변 상태이고, 원장의 수명이 cored 의 수명이 되면 프레임워크가 재기동한 뒤에도 죽은 창의 점유가 남는다)·`net_http_request`(전송기 하나가 `tokio` 를 끌고 오는데 이 프로세스의 게이트가 그것을 이름으로 막고, 시크릿 치환은 앱이 연 볼트를 읽는다)·`process_reclaim_window`(회수할 핸들은 자식을 스폰한 쪽의 것이라 cored 는 언제나 0 을 돌려주는데, 그 0 은 "거둘 것이 없었다"와 구분되지 않는다). 그리고 `webview_*`·`engine_*`·`titlebar_*`·`window_*` 는 영영 옮기지 않는다 — 프레임워크의 것이고, Electron 어댑터가 스스로 구현해야 한다.

## 프레임워크가 cored 를 세운다

Electron 은 더 이상 남이 차려 준 소켓을 기다리지 않는다. 자기 백엔드를 스스로 띄우고(`frameworks/electron/cored.cjs`) 정체성을 부팅 때 넘긴다.

- **홈은 프레임워크의 것이고 cored 에는 넘어간다.** 프레임워크는 identifier 만으로 홈을 파생하고(`app` 은 `~/.soksak`, 그 외는 `-<마지막 세그먼트>` 접미) 그것을 `--home`·`--identifier` 로 내려보낸다. 홈을 런타임에 갈아끼우는 통로는 없다 — 지목하는 것은 identifier 이고 홈은 그 결과다.
- **소켓은 `<home>/cored.sock` 이지 앱의 이름이 아니다.** 그 홈의 앱은 `<home>/<identifier>.sock` 에 bind 한다. 그 이름을 뺏으면 앱이 bind 할 자리에 cored 가 앉아 있고 앱은 "다른 인스턴스가 이미 돈다"로 거절당한다 — 자기 앱을 못 뜨게 만드는 백엔드다. 이름을 짧게 두는 것도 이유가 있다: 유닉스 소켓 경로에는 OS 상한이 있고 깊은 트리는 그것을 조용히 넘긴다.
- **외부 소켓은 붙기만 하고 거두지 않는다.** `SOKSAK_SOCKET`(또는 `--soksak-socket=`)이 지목하면 그 소켓은 남의 것이다: 프레임워크는 붙기만 하고 띄우지도 세우지도 않는다. 나갈 때 거두는 것은 프레임워크가 직접 띄운 cored 뿐이다. 이미 살아 있던 cored 도 같은 규칙 아래 있다 — 그것은 입양이고, 입양은 소유가 아니다.
- **바이너리는 추측하지 않는다.** 지목한 경로(`SOKSAK_CORED_BIN` 또는 `--soksak-cored=`)가 이기고, 그것이 없으면 발견 규칙으로 흘러내리지 않고 실패한다 — 흘러내리면 지목한 것과 다른 것을 실행한다. 지목이 없으면 이 저장소의 `debug`·`release` 빌드 자리를 차례로 보고, 어느 쪽에도 없으면 **찾아본 자리를 전부** 실어 실패한다. 지어낸 경로로 spawn 하면 `ENOENT` 한 줄만 남고 무엇을 어디서 찾았는지는 사라진다.
- **준비 완료는 cored 의 stdout 첫 줄이고, 그 줄은 그 소켓을 말해야 한다.** 프레임워크는 소켓 파일이 생기는지 지켜보는 대신 그 줄을 블로킹 read 로 기다린다: 파일 존재는 bind 완료가 아니고, 블로킹 read 는 cored 가 먼저 죽은 경우를 EOF 로 즉시 드러낸다. 다른 소켓을 말하는 준비 완료 줄도 실패다 — 띄운 것이 이 cored 가 아니거나 다른 곳에 붙었다는 뜻이고, 둘 다 그대로 두면 "붙은 척"으로 통과한다.
- **소켓을 쥔 채 남는 것은 없다.** 상한을 넘기면 프레임워크는 자기가 띄운 프로세스를 **거둔 뒤에** 알린다. 사유가 진짜 사유로 남고 고아가 경로를 쥐지 않는다. cored 쪽에도 짝이 되는 절반이 있다: 이미 그 경로를 서빙하는 것이 있으면 살아 있는 소켓을 지우지 않고 스스로 물러난다. 여기서 “서빙”은 유한 상한 안의 `system.hello` 왕복과 `role:cored` 응답이다. Unix `connect` 성공만으로는 부족하다. 자식이 listener FD를 상속하면 연결은 받으면서 cored 프로토콜에는 답하지 않을 수 있기 때문이다. 띄우는 쪽과 cored 싱글턴 게이트는 같은 프로브를 사용한다.

**Tauri 도 같은 걸음을 한다**(`frameworks/tauri/src/cored_host.rs`). 자리를 찔러 보고, 살아 있으면 채택하고 아니면 자기가 쥔 정체성으로 띄운 뒤, 그 연결로 `control_host_attach` 를 불러 자기 창을 등록한다 — cored 에는 창이 없으므로 밖에서 온 명령이 화면에 닿는 길은 창을 가진 쪽이 자기를 배달 통로로 등록하는 것뿐이다. 등록되지 않은 창 호스트는 명령을 받을 수 없으며 cored 는 `NO_HOST`로 거절한다.

- **채택은 바이너리 해소보다 먼저다.** `<home>/cored.sock` 이 실제로 서빙 중이면 Tauri 는 번들 sidecar 경로를 요구하지 않고 그 연결을 채택한다. 스폰 준비의 결함이 이미 살아 있는 공용 저장소 연결까지 끊어서는 안 된다. 자리가 비었을 때만 `SOKSAK_CORED_BIN` 또는 앱 실행물의 형제 `soksak-cored`를 해소한다.
- **앱 번들은 cored 를 함께 싣는다.** `make build-dev`·`make build-debug`·`make build`은 앱과 cored 에 같은 Cargo 프로필과 target triple을 명시하고 Tauri `externalBin`으로 `Contents/MacOS/soksak-cored`를 넣는다. Tauri가 요구하는 `<이름>-<target-triple>` 사본은 버전관리되지 않는 번들 입력일 뿐이며 최종 앱에는 실행물 하나만 남는다. HMR `make dev`는 번들이 아니므로 cored를 빌드만 하고 이 스테이징을 하지 않는다.
- **자리는 코어에서 한 번 파생된다**(`soksak_core::identity::cored_socket`). 두 프레임워크가 그 한 규칙으로 `<home>/cored.sock` 을 푼다. 철자가 둘이면 드리프트하고, 그 드리프트는 "연결 실패"로만 읽힌다.
- **자리에 프레임워크 축을 싣지 않는다.** 한 홈에 cored 는 하나이고 창을 가진 쪽이 여럿이다. 프레임워크마다 자리를 가르면 프레임워크 수만큼 백엔드가 서고, 저장소의 단일 쓰기 전제가 아무것도 실패하지 않은 채 사라진다.
- **앱의 자기 소켓은 그대로 선다.** 이 걸음은 붙는 것까지고 소켓을 합치지 않는다. 앱의 bind 철수는 `ipc_socket_path` 계약과 그것을 못박은 오라클(`crates/soksak-cored/tests/serves_over_socket.rs`)을 같은 커밋에서 함께 뒤집어야 하고, 여기서 미리 걷으면 앱을 겨눈 하니스가 통째로 주소를 잃는 중간 상태가 남는다.
- **새 창은 주소가 된 뒤에야 생성 완료다.** `window_create`는 새 살아 있는 창 사실을 보고하고 상관된 `control_windows` 응답을 받은 뒤 성공을 답한다. 폴링이 아니라 사건의 완료를 기다리는 것이다. `focus=false` 복원 창은 포커스 사건을 내지 않으므로 포커스를 등록 트리거로 쓸 수 없다. 등록이 실패하면 방금 만든 창을 파괴해 `window.list`와 cored 주소록이 서로 다른 사실을 남기지 않는다.
- **배달은 창을 다시 고르지 않는다.** 어느 창인지는 cored 가 코어의 규칙으로 이미 정했고, `ipc::request_in_window` 는 바로 그 창에서 실행한다. 여기서 다시 고르면 타겟 규칙이 두 벌이 되고, 두 벌은 갈리는 순간까지 조용하다 — 갈리면 사용자가 보고 있지 않은 창에서 명령이 돌고 성공을 답한다.
- **두 프레임워크가 든 라벨은 고르지 않고 거절한다.** 창 복원은 저장된 `w-<uuid>` 를 되쓰고 `main` 은 양쪽이 같은 철자로 쓰므로, 홈을 공유하면 겹침은 필연이다. cored 는 `AMBIGUOUS_HOST` 로 답하고 어느 쪽에도 보내지 않는다. 그 라벨은 PTY 재접속 키이기도 해서, 조용히 고른 결과는 남의 셸에 닿는다.

`frameworks/tauri/tests/attaches_to_cored.rs` 가 이것을 실제 소켓 위에서 몬다. 창 사실과 실행기를 주입하므로 GUI 없이 돌아간다: 등록, 배달, 배달 id 로 짝지어 돌아오는 회신, 새로 난 창, 죽은 창, 거절되는 겹친 라벨, 그리고 방송.

부채질은 발행에서 프레임워크가 지는 절반이다(`frameworks/electron/activity.cjs`). cored 는 적재하고 도장 찍힌 항목을 돌려주며, 프레임워크가 그것을 살아 있는 창 전부에 민다. 이것을 건너뛰면 프론트가 반환값을 버리므로 `listen("activity")` 구독자가 오류 한 줄 없이 굶는다. 적재분이 아닌 답은 밀지 않고 이름을 달고 거절한다 — 아닌 모양을 밀면 구독자가 조용히 어긋나고, 성공을 돌려주면 한 적 없는 배달을 했다고 답하게 된다.

두 파일 다 `electron` 을 require 하지 않는다. 프레임워크를 띄워야만 돌려볼 수 있는 코드는 사실상 검증되지 않으므로, 둘 다 `scripts/electron/cored-spawn.test.mjs` 와 `scripts/electron/framework-activity.test.mjs` 가 직접 몬다.

## 명령 표면이 갈리는 축

앱 명령 하나의 이식 여부를 가르는 물음은 "무엇을 하는가"가 아니라 **프레임워크 객체를 무엇 때문에 쥐고 있는가**다. 그 축이 표면을 셋으로 가른다.

- **A — 속성 하나에 걸렸을 뿐이다.** 핸들러가 프레임워크를 만지는 이유가 사실 하나다: 앰비언트 홈 읽기, 키로 쓰는 창 라벨. 그 속성이 값이 되면 핸들러가 풀리고, 로직은 아무것도 바뀌지 않는다.
- **B — 진짜 창의 것이다.** 자식 웹뷰·엔진·타이틀바·창. 이들은 영영 안 옮긴다. 두 번째 프레임워크가 스스로 구현하며, 두 번째 프레임워크가 지는 빚은 그것이 전부다.
- **C — `AppHandle` 이 상태 조회와 발행 때문에 있다.** `state::<T>()` 조회와 `activity::publish` 가 같은 함수 안에 있다. 이것을 풀려면 managed state 를 누가 소유하는지 바꿔야 하고, 그것은 동작 변경이라 이식이 아니라 별도 회차의 몫이다.

수는 여기 적지 않는다. 커밋마다 움직이고, 산문에 얼어붙은 수는 아무것도 실패시키지 않으면서 낡는 반면 그 수를 만들어 낸 판독기는 계속 옳다. 표면은 `frameworks/tauri/src` 아래의 `#[tauri::command]` 시그니처에서, `frameworks/tauri/src/lib.rs` 의 등록 목록(`generate_handler!`)에서, 그리고 그 시그니처를 이미 호출자-인자 집합으로 파싱해 두는 `cored_shape_gate::app_commands()` 에서 읽는다.

아래 비용이 한 곳에 뭉치는 이유가 B 이고, `ActivitySink` 가 진짜 결속이면서 동시에 나쁜 지렛대인 이유가 C 다.

## 두 번째 프레임워크의 실제 비용

이 저장소 실측(2026-07-27):

| 구획 | 규모 | 영향 |
| --- | --- | --- |
| 독립 러스트 크레이트(`soksak-ptyd`·`soksak-spec-*`·`soksak-seal`) | 5,686줄 | 없음 — 플랫폼 무관 |
| 사이드카(브라우저·터미널 엔진·db-studio) | 별도 프로세스 | 없음 — 소켓 프로토콜 그대로 |
| 설치 플러그인 전부 | — | 없음 — 벤더 import 0 |

| `frameworks/tauri/src` | 네이티브 표면 전체 | B 갈래가 어려운 부분 |

줄 수는 그 날짜의 실측이다. 명령 표면은 위에 적은 이유로 여기에 수로 얼리지 않는다 — 소스에서 읽는다.

깊은 결합은 흩어져 있지 않고 **네이티브 표면 층에 뭉쳐** 있다 — 자식 웹뷰, 투명한 DOM 영역의 마우스를 아래 네이티브 뷰로 통과시키는 hitTest 스위즐, 그 자식들까지 합성해 찍는 창 캡처. 영역 단위 히트 통과가 없는 프레임워크는 홀 계약을 지금 형태로 재현할 수 없고, 페이지만 찍는 캡처로는 픽셀 오라클을 돌릴 수 없다. 그러니 그것이 **가정할 부분이 아니라 먼저 만들어 볼 부분**이다.

Tauri의 네이티브 입력 브리지가 읽는 DOM 선언은 홀 수집기도 똑같이 읽는다. `.pane-gutter`와
`[data-native-drag]`가 가리키는 화면 사각형은 모두 `webview_dom_holes`에 실리며, 선언된
드래그 대상과 실제 네이티브 히트 홀이 서로 다른 선택자 집합을 가질 수 없다.

## 스파이크 모양

초판은 이랬다: "브라우저를 오프스크린 CEF 사이드카(프레임 스트림 → `<img>`)로만 띄우고 네이티브 자식 웹뷰를 1차에서 뺀다."

**Electron 에서는 그럴 필요가 없다.** CEF 사이드카는 WKWebView 가 못 그리는 것을 그리려고 만든 것인데 Electron 은 통째로 Chromium 이라 그 문제가 정의상 없다. 콘텐츠는 `<webview>` 로 페이지 안에 산다 — 프로세스는 갈리고(크래시 격리 유지), 제어면은 `loadURL`·`goBack`·`goForward`·`canGoBack`·`reload`·`stop`·`setZoomLevel`·`executeJavaScript`·`openDevTools`·`getURL`·`getTitle`·`insertCSS`·`capturePage`·`printToPDF` 로 그대로 있고, 겹침은 z-index 다.

그래서 임계 경로에서 빠지는 것이 홀·스위즐·합성 캡처만이 아니라 **사이드카 자체**다. 프레임 인코딩·전송·디코딩이 없으니 그 성능 질문도 함께 사라진다.

남는 질문은 셋이다: 새 다리를 지나는 명령 지연, 터미널 스트림 처리량, 멀티윈도우·포커스 동등성.

모든 기능이 이미 소켓 명령으로 노출돼 있으므로, 같은 제어면을 말하는 두 번째 프레임워크는 **기존 e2e 하니스를 그대로 판정기로 물려받는다.**

픽셀 오라클도 예외가 아니다. 그것은 어댑터 항목이지 예외가 아니었다 — 캡처는 이미 별도 플러그인(`tauri-plugin-webview-capture`)으로 갈려 per-OS 파일을 갖고 있고, 빠진 것은 그 능력이 `AppFramework` 계약에 없다는 것뿐이다. 계약에 넣으면 다른 능력과 같아진다. Electron 쪽 구현은 `capturePage` 다.

## 소켓 하나가 제어면이다

밖에서 온 명령 — 하니스·`sok`·에이전트 — 은 창에 닿아야 한다. cored 에는 창이 없어 그 명령을 실행할 수 없지만, Node 프레임워크가 닿을 수 있는 소켓을 여는 것은 그것뿐이다.

그래서 소켓 하나가 두 답을 갖는 표면이 됐다. cored 가 서빙하는 것은 cored 가 답하고, 나머지는 **창 호스트로 밀린다**. 부르는 쪽은 어느 쪽인지 몰라도 되고 봉투는 같다.

- **타겟 규칙은 코어의 것이다**(`soksak_core::control::resolve_target`). 포커스된 창 → `main` → 유일 워크스페이스 → 모호. `plugin.` 이름은 대신 마지막 포커스 워크스페이스로 간다 — 컨트롤 플레인에는 플러그인 호스트가 없어 그리로 보내면 상한까지 기다리고, 그 침묵은 "그런 명령이 없다"와 구분되지 않는다.
- **프레임워크가 호스트로 등록한다**(`control_host_attach`). 그 연결이 배달 통로가 된다. 프레임워크는 사실만 보고한다 — 살아 있는 라벨과 포커스된 하나. "마지막 워크스페이스가 무엇인가"는 규칙이고 코어의 `FocusLedger` 가 소유한다: 컨트롤 플레인 포커스가 워크스페이스 기억을 지우면 안 된다 — 자연어 콘솔은 `main` 에서 치지만 사용자의 무대는 다른 곳이다.
- **회신은 중계로 오지 않는다.** 창의 실행기가 `invoke("cmd_result", {id, result})` 를 부르고 그 호출은 여느 명령과 같은 다리를 탄다. 프로세스 종료처럼 그 다리를 파괴할 수 있는 부수효과는 executor의 `afterReply` 거래로 등록하고, `cmd_result` 전달이 성공한 뒤에만 실행한다. 전달 실패 시 부수효과를 실행하지 않아 호출자가 재시도할 수 있어야 한다. 중계에 돌아오는 길을 만들면 명령 하나가 두 길로 답한다.
- **임자 없는 사실은 방송한다.** 파일 변경에는 수신자가 없다. cored 가 `{"broadcast": {event, payload}}` 를 밀고 프레임워크가 창 전부에 뿌린다. 배달과 방송은 키가 다르다 — 배달은 답을 기다리고 방송은 답이 없다. 같은 키면 받는 쪽이 없는 id 로 회신하려 든다.

기본 응답 상한보다 오래 걸릴 수 있는 유한 명령은 호출자가 공개 소켓 봉투의 `timeoutMs`를
선언한다. 명령 params에 섞거나 고정 sleep·재시도·비동기 완료 위장으로 우회하지 않는다.

**창의 자기 다리로 온 것은 그 창으로 되돌리지 않는다.** 렌더러는 `pty_pane_alive` 를 같은 소켓으로 묻는다. "서빙 안 하면 창으로 민다"였을 때 그것이 물어본 바로 그 창으로 갔고, 그 창의 실행기에는 그 이름이 없어 부른 쪽은 이름 대신 10초를 기다렸다. 가르는 축은 철자가 아니라 **누가 물었는가**이고, 그것은 연결이 안다. 다리가 자기를 밝히고(`control_bridge_attach`) 그 연결의 미서빙 이름은 즉시 `NOT_SERVED_HERE` 로 답한다. 이 한 수정으로 부팅 요구가 1,181건에서 100건으로 줄었다 — 나머지는 상한 뒤의 재시도였다.

## 답 하나에 안 담기는 것

터미널 출력과 프로세스 stdout 은 요청/응답 한 쌍에 안 담긴다. 부르는 쪽이 받을 자리를 함께 보낸다: 인자 어딘가에 토큰 하나가 실리고, 그 뒤로 프레임이 그 토큰을 달고 온다.

토큰의 **실체**는 프레임워크마다 다르다 — Tauri 는 `Channel`, Electron 은 프리로드가 만든 id — 그리고 둘 다 함수로는 프로세스 경계를 못 넘는다. 소켓 위에서는 어느 쪽이든 토큰이라, `soksak_core::stream` 이 토큰을 찾고·프레임을 만들고·명령의 몸이 보기 전에 인자에서 지우는 일을 소유한다. 몸이 토큰을 알면 명령마다 무시 규칙을 따로 배워야 한다.

프레임은 **부른 연결**로 간다. 다른 연결은 그 토큰을 만들지 않은 쪽이라 프레임을 버린다 — 오류 없는 유실이다. 매는 일은 실행보다 먼저다: 명령이 첫 프레임을 곧바로 밀 수 있고, 갈 곳 없는 프레임은 조용히 사라진다. 연결이 끝나면 그 토큰도 끝난다.

**토큰은 직렬화를 견뎌야 한다.** 토큰에 `onmessage` 접근자를 **열거 가능하게** 얹었더니 `invoke` 가 경계에서 `An object could not be cloned` 로 죽었다 — 구조화 복제는 열거 가능한 자기 속성을 읽는데, 그 getter 가 함수를 돌려주고 함수는 복제되지 않는다. `spawn_terminal` 은 한 번도 서버에 닿지 못했고, 증상은 "터미널이 안 뜬다" 하나였다(보낸 적이 없으니 요구 원장에도 안 남았다). 접근자를 열거되지 않게 고쳤다. 검사는 모양을 보지 않고 **복제를 실행한다** — 모양만 보면 같은 결함을 다시 놓친다.

## 남은 중복 — dev-의존이 그것을 가리킨다

`frameworks/tauri/Cargo.toml` 의 `[dev-dependencies]` 에 `soksak-cored` 가 있다. 뜻은 하나다:
**출하되는 앱 바이너리에는 cored 코드가 한 줄도 없다.** 앱은 자기 백엔드를 통째로 따로 갖고 있고,
그 dev-의존은 오직 검사 때 "두 표가 어긋났나"를 대조하려고 있다(`cored_shape_gate.rs`).

대조할 표가 둘이라는 것 자체가 결함이다. 그래서 이 항목은 원칙이 아니라 **남은 일의 표지**다 —
백엔드가 하나가 되면 표도 하나이고, 그때 게이트와 dev-의존이 함께 끝난다. 먼저 지우면 그것이
잡던 어긋남만 다시 조용해진다(실측 2026-07-28: cored 가 서빙한다고 믿었던 5개가 라이브 부팅에서
전부 `INVALID_PARAMS` 였고, 그 거절은 프레임워크 로그 한 줄이었다).

## 구현 둘, 픽스처 하나

어떤 규칙은 한 곳으로 모을 수 없다. 그 규칙이 다루는 것을 프레임워크가 진짜로 소유하기 때문이다.

프로젝트 점유 지도가 가장 분명하다: 그 수명이 **곧 창의 수명**이다. cored 가 쥐면 죽은 창의 점유가 프레임워크 재기동을 넘어 살아남아 그 프로젝트를 다시 못 연다. 그래서 지도는 창을 소유한 쪽에 남고 — 그것은 구현이 둘이라는 뜻이다.

**지도**가 둘인 것은 옳다. **규칙**이 둘인 것은 아니다: 같은 조작이 프레임워크마다 다르게 답하면 오류로 드러나지 않고 "이쪽에서만 프로젝트가 안 열린다"로 나타난다.

그래서 픽스처가 묶는다. `crates/soksak-core/fixtures/*.json` 에 사례가 있고, Rust 검사와 JS 검사가 같은 파일을 읽는다. 한쪽만 고치면 그쪽이 깨진다. 사람 주의력이 아니라 파일이 묶는다.

| 픽스처 | 묶는 것 |
| --- | --- |
| `monitor-of.json` | 창이 어느 모니터의 것인가(중심점·경계·버림 방향) |
| `project-claims.json` | 점유·같은 창 멱등·값으로서의 실패·소유 창만 해제·죽은 창 걸러내기 |
| `window-rect.json` | rect 유효성·포커스 기본·워크스페이스 라벨 모양 |
| `surface-spec.json` | `#rrggbb` 색·열 수 있는 URL 스킴 |

`window_monitors` 는 왕복으로 바꿔 봤다가 되돌렸다: 창마다 프로세스를 건너고, 백엔드가 없으면 프레임워크 사실이 죽는다. 얇은 배선 게이트는 그 실측을 항목 옆에 적는다 — 거기서 오판의 대가는 "고쳐라"가 아니라 "선언하라"다.

## 자원은 프레임워크가 아니다

cored 의 의존성 게이트는 프레임워크와 네이티브 런타임을 이름으로 막는다. 그것은 `rusqlite` 가 왜 예외인지 이미 소리 내어 적어 두었다: 저장소는 창을 열지 않고 앱 핸들을 쥐지 않으며, 어느 프로세스에서 읽든 같은 파일을 같은 답으로 읽는다.

`notify` 도 같은 판정을 통과한다 — 파일시스템 사건은 자원이고, cored 가 `watch_dir` 을 서빙하려면 그 핸들을 져야 한다. 두 크레이트 모두 `soksak-core` 에서는 여전히 금지다(코어는 무의존을 지킨다). 규칙은 그 곁의 작은 크레이트에 산다(`soksak-watch`, `soksak-store`).

`tokio` 는 통과하지 못한다. `net_http_request`·`download_verify`·`sidecar_ensure`·`media_proxy_info` 가 그 때문에 미서빙으로 남는다 — 전송기가 하나(`wreq`)이고 그것이 런타임을 끌고 오며, 게이트는 프레임워크만이 아니라 런타임도 이름으로 막는다. 구멍을 메우려고 기준을 낮추지 않는다.

그러나 그 두 크레이트에서 막힌 것이 모든 곳에서 막힌 것은 아니고, HTTP capability 와 미디어 프록시가 그것을 보였다. 둘의 몸은 창을 열지도 앱 핸들을 쥐지도 않는다 — 자기가 세든 프레임워크의 이름을 한 번도 부르지 않는 892줄이었고, 그런 코드가 프레임워크 이름 밑에 남으면 두 번째 프레임워크가 같은 전송 규칙을 다시 쓴다. 지금은 `crates/soksak-net` 에 산다. 그 크레이트가 `tokio` 와 `wreq` 를 혼자 지고, 자기 의존성 검사로 프레임워크를 막는다. 각 프레임워크에는 명령 래퍼와 이 프로세스가 든 손잡이만 남는다.

그 이관에서 프로세스 전역 둘이 죽었다. 프록시의 포트와 토큰이 `OnceLock` 한 쌍이었는데, 그것은 옆에 있는 공용 client·런타임과 다른 것이다: client 는 **자원**이라 어느 인스턴스로 보내도 같은 요청이 같은 응답을 받지만, OS 가 할당한 포트와 기동 때 뽑은 난수는 **답**이라 규칙으로 되짚을 수 없다. 전역 한 칸에서는 두 번째 `start()` 가 조용히 무시되고 첫 번째의 포트가 답으로 나갔고, 그래서 검사는 자기 프록시를 세울 수 없었다. 지금은 `start()` 가 `MediaProxy` 손잡이를 돌려주고, 그것을 든 쪽이 답한다.

## 터미널에 필요했던 것

셸은 `soksak-ptyd` 가 소유하고 앱 재시작을 넘어 산다. 그 데몬에 붙는 클라이언트가 앱 크레이트에 있어서, 두 번째 프레임워크는 같은 데몬에 닿을 길이 없었다 — 그리고 붙는 방식이 둘이면 같은 세션이 한쪽에서는 살아 있고 다른 쪽에서는 죽은 것으로 보인다.

그 클라이언트를 코어로 옮기며 결합 셋을 떼어 각각 계약으로 바꿨다: 볼트(`SealKeys`), 세션 등록부(`Arc` 로 지고 가는 `Link`), 원장(`ActivitySink`). 셸 env 규칙도 함께 옮겼다 — 화이트리스트가 두 벌이면 시크릿 유출이 프로세스마다 다르고, 그것은 오류가 아니라 조용한 구멍이다.

cored 는 터미널을 로컬 폴백 없이 서빙한다. 앱은 데몬을 못 잡으면 인프로세스 PTY 로 떨어지지만, 헬퍼가 그러면 앱 재시작이 지키려던 바로 그 셸이 헬퍼의 종료와 함께 죽는다. 못 붙으면 이름을 달고 거절한다.

## 콘텐츠 뷰 이음매가 치른 값

이 프레임워크에서 콘텐츠는 페이지 안에 산다 — 네이티브 형제가 아니라 `<webview>` 요소다. 위 스파이크 절은 제어면이 다 있다고 적었다. 그것을 실제 하니스 앞에 세우자 결함 넷이 나왔고, 넷 다 서로 다른 방식으로 조용했다(실측 2026-07-28):

| 결함 | 증상 | 왜 안 보였나 |
| --- | --- | --- |
| 태그 사건을 `CustomEvent.detail` 로 읽음 | 페이지는 렌더됐는데 주소창이 `about:blank` 에 멈춤 | 단위 검사가 `CustomEvent` 를 던져 detail 을 읽는 코드가 통과 |
| 전역 `listen` 이 로컬 버스를 안 이음 | `emitLocal` 로 나가는 모든 사건이 전역 구독자에게 미도달 | 창-스코프 `listen` 은 이미 둘을 이었고 전역만 어긋남 |
| 게스트 스크립트를 함수 본문이 아니라 스크립트로 전달 | `dom.text`·`eval` 이 `1+1` 조차 실패 | 오류 문구가 "Script failed to execute" 라 페이지 탓으로 읽힘 |
| 닫은 창의 영속 흔적이 남음 | 컨트롤 창 재적재에 닫힌 창 15 개가 부활 | Tauri 는 `Destroyed` 에서 지우는데 이 프레임워크엔 그 자리가 없었음 |

넷이 되돌린 계약은 모양이 같다: 그 규칙은 어느 프레임워크의 것도 아니므로, 둘 다 부르는 자리로 옮긴다. 흔적 폐기는 이제 `soksak_core::window_traces` 이고, 앱은 자기 연결로 이 프레임워크는 cored 의 `window_traces_prune` 으로 부른다. 게스트 스크립트는 WKWebView 계약(`callAsyncJavaScript` 는 비동기 함수 본문을 받는다)을 그대로 두고 어댑터가 감싼다 — 계약을 다시 정의하지 않는다.

오늘 이 프레임워크를 상대로 하니스가 내는 판정: `p0-contracts` 24/0, `multiwindow` 16/0, `tab-switch-ghost` 13/0, `rail-border` 5/0, `window-traces` 4/0, `motion-slow` 11/0, `surface-park` 8/0, `slot-freeze` 전체 GREEN, `ui-verify`·`gutter-hover` GREEN.

## 어떻게 다른지 말할 자리

`surface-park`·`slot-freeze`·`gutter-drag` 는 **네이티브 자식 표면**을 읽었다 — `webview_list`, 엔진 서피스 통계, 합성된 자식의 rect. 이 프레임워크에서 그것들은 구조상 비어 있고, cored 는 숫자를 지어내는 대신 `FRAMEWORK_CONCEPT_ABSENT` 로 답한다. 판정하는 쪽에는 그 사실을 **물을 자리**가 없었다.

`framework.provision`이 그 자리다. `chromium`·`nativeChildWebview`는 렌더링 기반을 설명하고,
`supportsDocumentStart`·`supportsInputInjection`은 제품에 보이는 선택 기능을 설명한다. `name`은
원장·진단에만 쓴다. 합성 구현 분기는 capability 조합표가 아니라 어댑터 선택 한 곳에 남는다.
활성 브라우저가 실제로 서는지는 네이티브 표면 목록 또는 문서 안 본문의 rect로 판정하며, DOM-only
껍데기는 네이티브 슬롯 착지를 지어내지 않고 사유와 함께 비적용으로 보고한다.

그 과정에서 거짓 GREEN 이 나왔다. `gutter-drag` 의 축 격리 검사는 두 겹으로 공허했다 — 구동을 네이티브 입력으로만 해서 그 명령이 없는 프레임워크에서는 아무것도 안 끌었고, 높이 오라클이 rect 없는 트리를 읽어 `-1` 끼리 비교했다. 재는 자리를 고치자 곧바로 진짜 실패가 드러났다.

## "다 됐다"가 가리고 있던 것

이식을 완료라고 말할 수 있었던 것은 **빠진 것을 세는 자리가 없었기** 때문이다. 앱이 부르는 백엔드 이름은 177 개이고, 그중 67 개를 이 프레임워크에서 아무도 답하지 않는다. 64 개는 Tauri 에 있다. 런타임은 그 전부를 `FRAMEWORK_CONCEPT_ABSENT` 로 답했는데, 그 코드는 성질이 다른 두 사실을 한 통에 담는다: *이 프레임워크에 개념이 없다*(네이티브 자식 표면)와 *아직 옮기지 않았다*(스케줄러·시크릿·클립보드·웹소켓, 그리고 `data_*` 저장소 표면 전체). 섞이면 후자가 전자의 얼굴을 쓰고 영원히 남는다.

`scripts/gates/command-ownership.mjs` 가 분류를 소스에서 읽는다 — cored 표, 각 프레임워크 표, Tauri 등록. 그 곁의 장부에는 사유와 **갈 자리**(`core`·`framework`·`renderer`·`unserved`)만 산다. 다음 사람이 "어디에 붙일까"를 다시 판단하지 않게 하기 위해서다. `cap` 은 래칫이다: 이식 없이 표면을 늘리면 실패하고, 이미 누군가 답하는 이름이 장부에 남아 있어도 실패한다 — 갚은 것을 부채로 들고 있으면 수가 거짓이 된다.

### 사유는 답이 아니다 (2026-07-30 재입법)

그 래칫에 구멍이 있었다. `cap` 은 **미선언 공백**만 셌고, cored 가 사유를 달고 거절한 이름(`refused`)은 세는 자리를 벗어났다. 사유를 적는 순간 그 이름이 장부에서 사라지고, 영원히 안 답해도 게이트가 통과했다.

부른 쪽에서 "선언거절"과 "미선언공백"은 같은 사실이다: **값이 안 온다.** 실측 — `sidecar_open` 이 선언거절에 앉아 게이트를 통과하는 동안 두 번째 프레임워크의 렌더러는 그 이름을 139번 부르고 139번 `NOT_SERVED_HERE` 를 받았다. 브라우저 엔진이 뜨지 못했고 화면에는 "엔진 서피스 생성 실패"만 남았다.

그래서 래칫이 둘이다. `cap` = 미선언 공백(사유를 적는 일이 진전으로 보이게), `unansweredCap` = **답이 없는 이름 전체**(선언거절 + 미선언공백). 후자는 사유를 적어도 안 줄고, 누군가 실제로 답할 때만 줄어든다. 부재 선언(`absent`)은 여기 안 든다 — 증명된 부재는 확정된 답이다.

현재: 답이 온다 114(`core` 77 · `framework` 15 · `renderer` 13 · 부재선언 9) · **답이 없다 62**(선언거절 35 · 미선언공백 27).

### 시그니처는 소유의 증거가 아니다

이식 장부(`cored_ledger.rs`)에도 같은 종류의 거짓이 있었다. `lane_of` 가 시그니처에 `Window` 가 주입되면 `framework` 갈래로 셌는데, 두 번째 프레임워크는 **이름 접두**로 자기 몫을 고른다(`native/index.cjs` 의 `BRANCHES`). 가족 밖 이름은 그 표에 안 걸려 소켓으로 새고 cored 도 안 서빙하는데, 장부는 "프레임워크가 답할 몫"으로 세어 이식 대상에서 뺐다 — **아무도 안 가진 명령이 다 옮긴 것처럼 세어졌다.** 넷이 그랬다: `sidecar_open`·`sidecar_send`·`process_reclaim_window`·`daemon_start`.

창을 주입받는다는 것이 창의 개념이라는 뜻은 아니다. 사이드카는 OS 프로세스이고 창은 그 사건을 돌려줄 **주소**로만 쓰인다. 주입은 소유가 아니라 결합의 증거이므로 `state-bound` 로 간다 — 그 결합을 푸는 것이 곧 이식이다. `framework` 48 → 42 · `state-bound` 51 → 57.

두 가족 목록이 한 벌인지도 이제 게이트가 지킨다(`FRAMEWORK_FAMILIES` ≡ `BRANCHES`).

### 첫 상환: `download_verify`

규칙이 정직해지자 갚을 것이 보였다. `download_verify` 는 창도 앱 핸들도 볼트도 안 쓰는 열 줄인데, 막는 것은 `tokio` **이름 하나**뿐이었다 — 그리고 그 이름은 금지 목록 **자신의 기준**(창을 여는가·앱 핸들을 쥐는가·프로세스마다 답이 갈리는가)에 걸리지 않았다. `soksak-net` 은 같은 기준으로 이미 "tokio 는 자원"이라고 자기 헤더에 적고 있었다. 한 저장소가 같은 크레이트를 두 규칙으로 판정하고 있었다.

그래서 이름을 풀고 그 커밋에서 바로 서빙한다(쓸 곳 없이 미리 여는 것은 결정을 감추는 것이다). 판정과 쓰기는 코어의 `verify_and_write` 하나가 지고, Tauri 진입점도 같은 함수를 부른다 — 사본을 두면 두 프로세스가 같은 이름에 다른 규칙을 갖고, 그 차이는 오류가 아니라 **다른 파일**로 나타난다. 이 프로세스의 동시성 모형은 안 바뀐다: `soksak-net` 이 sync 표면만 노출하고 런타임을 자기 안에 가둔다.

`unansweredCap` 62. 남은 `unserved` 셋은 `ws_*` 뿐이다.

## 관측면도 이식의 일부다

골 드래그가 첫 이동에서 죽었다. 제스처는 정확히 서는데 pane rect 는 내내 불변이었고, 조사는 "안을 볼 방법이 없다"에서 멈췄다 — 그것은 진단이 아니라 **없는 표면**이다. `ui.input.observe` 가 창에 실제로 도착하는 입력을 capture 단계에서 기록한다. 그러면 실패가 *이벤트가 안 갔다* 와 *갔는데 안 움직였다* 로 갈린다.

한 판에 답이 나왔다: 첫 이동과 **같은 순간·같은 좌표**로 `mouseup` 이 골에 꽂혔다. 코어의 포인터 순서 복구가 "눌린 채인데 `buttons === 0` 인 mousemove" 를 유령 홀드로 보고 합성하는 그것이다 — macOS 창 활성화 클릭이 up 을 유실하는 것에 대한 옳은 보호다. 주입한 이벤트에 `buttons` 가 없어 기본값 0 이었고, 그래서 **주입한 드래그가 스스로를 죽였다.** 계약 둘이 각자 옳은 채로 그 사이에서 기능이 죽었다. Tauri 는 골 드래그를 네이티브 다리로만 몰아 이 경로를 걷지 않았다.

그 다리 자체가 이식해야 할 표면이었다: `webview_emit_native` 는 네이티브 모니터가 내는 `native-mouse*` 사건을 그대로 발행한다. 그 자리가 비면 실마우스 없이 그 제스처를 구동할 길이 없다.

이 프레임워크에서 하니스 열둘이 전부 GREEN 이다.

## 껍데기는 껍데기다 (2026-07-30 명제)

**프레임워크 폴더에는 동작 코어를 남기지 않는다 — 닿든 안 닿든, 예외 없다.** Tauri 와 Electron 은 같은 층위의 껍데기이고, 코어는 공통으로 간다.

접촉(`tauri::`)의 유무나 밀도로는 이 법을 못 잰다. 671줄 중 22줄이 프레임워크를 부르는 파일은 프레임워크 파일이 아니라 **그 폴더에 사는 코어**인데, 접촉을 세는 눈(`framework-free-tenant`)에는 정상으로 보인다. 그래서 **몸**을 센다: `baseline-gate` 의 `framework-body` 지표가 파일별 코드 줄 수(주석·빈 줄 제외)를 봉인하고, 봉인은 내려가기만 한다. 올리는 것은 명시 재입법이고, 그때 그 증가가 배선인지 코어인지 적는다.

착수 실측: `frameworks/tauri/src` 53파일 **17,567줄** vs `frameworks/electron` 15파일 **1,598줄**. 같은 일을 11배로 하고 있고, 그 차이가 곧 옮길 양이다.

### 무엇이 껍데기에 남는가

셋뿐이다. 각각 **프로세스를 못 건너기 때문에** 남는다.

| 남는 것 | 왜 |
|---|---|
| 네이티브 부모 표면 | 부모 뷰는 프로세스-로컬이다 — 다른 프로세스가 대신 줄 수 없다 |
| 메인스레드 실행 | 그 프로세스의 런루프다 |
| 사건 싱크 | 사건은 그 창의 구독자에게 가야 한다 |

그 밖은 전부 공통이다. 이름 가족이 아니라 **무엇을 만지는가**로 가른다: `sidecar_open/send/close` 는 in-process 엔진이라 껍데기의 것이지만, 같은 접두의 `sidecar_ensure`(내려받기+해시)와 `sidecar_dev_new`(파일 골격)는 코어의 것이다.

**대부분의 벽은 벽이 아니었다.** `unserved.rs` 의 거절마다 무엇이 막는지 적혀 있는데, 그 사유를 코드와 대조하니 참인 경우보다 낡은 경우가 훨씬 많았다.

"이 프로세스의 열쇠 이음매는 `NoSealKeys` 뿐" — 볼트 몸은 이미 프레임워크 밖이었고, 실제로 없던 것은 **OS 키체인 어댑터**였다. 그것이 껍데기 폴더에 남아 있었다. 키체인은 *플랫폼* 자원이지 프레임워크 자원이 아니다: 볼트 파일은 홈에 사는데 그 열쇠가 프레임워크로 갈리면 파일과 열쇠가 서로 다른 축이 되고, 홈을 공유해도 둘째 껍데기는 그 볼트를 못 연다. `keyring` 을 볼트 크레이트로 옮기니 열둘이 섰다.
- **상주 서비스**가 넷을 막았다. "매니저가 요구하는 호스트 능력에 대응하는 계약이 코어에 없다" — 계약(`ServiceHost`)은 크레이트에 있었고, 그 다섯 중 넷은 cored 가 이미 지는 것들이다(활동 발행·예약 깨우기·시크릿 둘). 다섯째인 중개는 cored 의 단일 갈래 *그 자체*다.
- **`service_ledger_sync`** 의 사유("파일 쓰기와 결속 맞춤이 한 손이어야 한다")는 옮기지 못할 이유가 아니라 **함께 옮겨야 할 것의 목록**이었다.
- **유닛 설치**가 다섯을 막았고 벽은 셋이었다. 그중 하나는 벽이 아니라 **결함**이었다: 매니저 생성자가 스테이징을 통째로 비워서, 두 번째로 만든 프로세스가 남의 진행 중 트랜잭션을 명령 이전에 지운다. 생성과 비우기를 갈랐다(`clear_staging`, 부팅에서 한 번). 다른 하나 — "원장이 프로세스 메모리라 `begin` 과 `commit` 을 다른 프로세스가 잡으면 실패뿐" — 은 나눠 옮기는 것에 대한 반론이지 옮기는 것에 대한 반론이 아니었다.
- **`unit_dev_*`** 의 벽은 **프로세스 안의 `Mutex`** 였고, 그것은 프로세스 둘을 못 막는다: 각자 자기 것을 잡고 서로를 못 보므로, 겹친 read-modify-write 가 남의 선언을 지운 채로 *성공을 답한다*. 그 손실은 오류로 보이지 않는다 — 파일은 멀쩡하고 내용만 뒤로 돌아간다. 이제 커널 권고 파일 잠금이다(`soksak_core::file_lock`).

**옮기다가 드러난 갈래 둘.** 두 명령이 어느 프로세스가 답하느냐에 따라 다르게 동작했고, 어느 쪽도 오류로 드러날 수 없었다.

1. 쓰기 재시도와 실패 증거가 껍데기에만 있었다. cored 가 쓰기를 서빙하기 시작한 뒤로 그 경로는 앱 경로가 네 번 견디는 실패를 그대로 사용자에게 돌려줬다.
2. 백업 링의 유일한 트리거가 껍데기의 쓰기에만 걸려 있었다. cored 를 지나는 쓰기는 링을 **한 번도** 안 돌렸다 — 사고가 나야 값을 치르는 부채다.

**순서도 계약이다.** 간헐 실패 하나에 진짜 원인이 있었다. 한 연결의 프레임은 각자 스레드로 간다(요청 하나 = 스레드 하나). 그래서 연결 *선언*이 첫 명령보다 먼저 줄에 오르고도 나중에 설 수 있었고, 그 창의 다리로 온 요청이 그 창으로 배달되어 회신할 자리가 없었다. 순서를 보장한다고 적힌 주석은 연결 하나 = 스레드 하나였을 때 쓰인 것이다. 선언은 이제 읽은 자리에서 선다.

### 그 뒤 무너진 벽 넷

`update_check` / `update_apply` — 앱 실행물을 갈아 끼우는 일은 그 실행물을 아는 쪽만 할 수 있어 **이 프레임워크가 답한다**. 채널 게이트가 먼저다: dev·debug 홈의 본체는 로컬 빌드라 원격 조회 자체가 성립하지 않고, 그때의 `available:false` 는 *"이 채널은 원격을 안 본다"*이지 *"새 판이 없다"*가 아니다. 두 사실을 같은 모양으로 답하면 부른 쪽이 가릴 수 없어 channel 을 함께 싣는다. release 채널은 **이름을 달고** 거절한다: 서명 검증된 번들을 받아 설치하는 장치가 배선되지 않았고, 없는 장치를 `available:false` 로 답하면 그것은 *"최신이다"* 라는 거짓이라 사용자가 오지 않을 업데이트를 영원히 기다린다.

`unit_dev_set` / `unit_dev_remove` — 벽은 프로세스 안의 `Mutex` 와 몸의 자리였고 둘 다 사라졌다. 옮기다 다른 것이 드러났다: **같은 것 넷이 두 자리에 글자 그대로 살고 있었다**(`CONFIG_FILE`·`CONFIG_VERSION`·`UnitDevConfig`·`config_path`). 읽기는 코어가, 쓰기는 껍데기가 각자 자기 사본을 들고 같은 파일을 만졌다. 두 벌은 갈리는 순간까지 조용하다.

**창 라벨.** 배달은 이미 겹친 라벨을 이름으로 거절했지만(`AMBIGUOUS_HOST`), *목록*은 합쳐서 하나로 답했다. 창 복원은 라벨을 새로 만들지 않고 저장된 `w-<uuid>` 를 의도적으로 되쓰므로, 한 홈을 두 프레임워크가 보면 같은 슬롯을 각자 되살린다. 목록을 하나로 읽은 쪽은 창이 하나라고 믿고 그 위에 판단을 세운다. `window_census` 는 라벨마다 그 라벨을 든 호스트 수를 답한다 — **어느 창인지 못 고르는 것과 창이 하나인 것은 다른 사실이고**, 그 겹침을 이미 명령을 보낸 뒤에 오는 실패로 배울 필요는 없다.

`plugin_dev_*` 는 벽이 남았고, 사유의 절반을 지웠다. 쓰기 쪽 벽은 사라졌고 남은 것은 git 스폰이며 그것은 지금 서 있는 규칙이다 — `core-git-scan` 이 코어·크레이트 전체에서 git 매칭을 0 으로 봉인하고 열린 자리는 명시 allowlist 한 파일뿐이다. **틀린 사유는 없느니만 못하다**: 무너진 벽을 남겨 두면 그 이름은 다시 조사되지 않는다.

### 마지막 가족: 벽은 셋이었고 참인 것은 하나였다

`sidecar_open` / `send` / `close` 는 셋이 한꺼번에 막는다고 적혀 있었다 — 동적 적재, 네이티브 뷰, 창 채널. 다시 재니 하나만 참이었다.

**동적 적재는 프레임워크가 아니라 OS 호출이다.** `libloading` 은 금지 목록 **자신의 기준**(창을 여는가·앱 핸들을 쥐는가·프로세스마다 답이 갈리는가) 어디에도 걸리지 않는데 이름으로 막혀 있었다 — `tokio` 와 똑같은 자리다. 이름 하나가 명령 셋을 이 프로세스 밖에 묶어 두고 있었다.

**메인스레드는 창을 요구하지 않는다.** 엔진의 `init`·`shutdown` 이 요구하는 것은 "이 프로세스의 첫 스레드"뿐이다. 그 자리를 accept 루프에 쓰고 있었다 — 없어서 못 준 것이 아니라 **내준** 것이다. accept 는 어느 스레드에서나 같은 답을 내지만 엔진 init 은 그렇지 않다. 자리를 바꾸고 루프를 옆으로 옮겼다.

**네이티브 부모 표면은 정말로 없고**, 그 하나만 참으로 남는다. 매 메시지에 실리는 표면 포인터는 `0` 이다. 지어내지 않는다: 가짜 포인터는 유효한 주소로 읽혀 엔진이 남의 메모리에 자기 표면을 얹는다. 표면을 **쓰는** 엔진은 그 순간 자기 이름으로 실패한다. 호스팅 크레이트의 `surface_alive` 가 빈 기본구현인 것이 바로 이 경우를 위한 자리다 — 네이티브 자식 표면이 없는 호스트는 편입할 것이 없다고 설계가 이미 적어 두었다.

사건은 **부른 쪽의 스트림 토큰**으로 간다. 창 채널이 없다는 것이 방송할 이유가 되지 않는다: 방송은 미개봉 코드에도 배달되고, 그 누수가 이 표면이 처음부터 막던 것이다.

쓸 곳 없이 미리 열지 않았다 — `libloading` 이 풀린 커밋이 곧 그 셋을 서빙하는 커밋이다.

### 아무도 읽지 않은 계약

이식이 끝났다고 불렸고, 그 앱은 **한 번도 안 띄워졌다.** 둘 다 세워 보니 마지막 결함이 나왔는데, 그것은 옮긴 것 안이 아니라 **적어 두고 안 읽은 것** 안에 있었다.

두 프레임워크가 `engineProvision` 을 채운다(이 웹뷰가 chromium 등급인가·네이티브 자식 뷰를 합성할 수 있는가). 스펙은 플러그인의 요구와 그것을 대조하라고 `unmetNeeds` 를 내보낸다. **아무도 그것을 부르지 않았다.** 그래서 네이티브 자식 뷰를 전제한 표면이 그 장치가 없는 프레임워크에서도 적재됐고, 화면에는 "엔진 서피스 생성 실패"만 남았다 — 없는 것이 아니라 고장으로 읽히는 문장이다.

계약을 적어 두고 읽지 않으면 없는 것과 같다. 대조는 이제 활성화 경계에서 한 번 일어나고, 그 결과는 **말해진다**: 무엇이 모자라서 빠졌는지가 플러그인 상태에 이름으로 남아, 다음 사람이 다시 조사하지 않고 사용자도 "고장"이 아니라 "이 프레임워크에 없는 표면"으로 읽는다.

**요구는 묻지 않고 파생한다.** `docs/SIDECARS.md §1` 이 이미 적어 뒀다: `engine` 모델은 in-process dylib 이고 그 Surface 칸은 *renders into pane surfaces (NSView)* 다. 표면 없는 engine 은 그 정의상 없다. 저자에게 `requiresNativeChildWebview: true` 를 다시 적게 하는 것은 매니페스트가 이미 지고 있는 사실의 **두 벌**이고, 두 벌은 갈릴 때까지 조용하다 — 실제로 그렇게 갈렸다.

**권한은 열어 둔 문이지 지나간 자국이 아니다.** 첫 판은 `sidecar` 권한을 엔진 사용의 증거로 읽어, 그 권한을 과선언했을 뿐인 헤드리스 플러그인을 떨궜다. 서비스 모델의 증거는 `service` 선언이다 — 스펙이 그 자리를 그 뜻으로 이미 두고 있다.

### 축은 둘이다

첫 판은 엔진 요구를 `requiresNativeChildWebview` 로 파생했다. 결과는 맞았고 **사유가 거짓이었다.**

`docs/SIDECARS.md §8` 이 두 합성 모드를 적어 뒀다: `windowed` 는 네이티브 자식 뷰를 창 아래 붙이고, `offscreen` 은 엔진이 자기 레이어에 그린다(픽셀은 프로세스 안 GPU 핸들로만 움직인다). 자식 뷰가 필요한 것은 앞의 하나뿐이다. 둘이 함께 필요로 하는 것은 다른 것이다 — **이 프로세스가 그 모듈을 들일 수 있는가**(dlopen + 메인스레드 + 창).

그래서 축을 따로 세웠다: `engineModules`. 프레임워크가 각자 자기 사실을 채운다 — Tauri 는 백엔드가 Rust 라 열고, 이 프레임워크는 메인 프로세스가 JS 라 못 연다. 네이티브 애드온을 붙이면 달라지는 값이라, **못 하는 것이 아니라 아직 안 붙인 것**이다.

두 축을 뭉치면 offscreen 소비자가 **원한 적도 없는** 자식 뷰의 부재로 거절당한다. 결과는 똑같아 보이고, 다음 사람은 엉뚱한 것을 고치러 간다.

### 바꾸지 않는 것과 그 이유

offscreen 축은 코어의 공백이 **아니다**. 2026-07-08 에 검증됐고 일부러 엔진 프로토콜 어휘에 산다 — *코어 변경 0*. 그 기록을 읽고 나서 여기서 내렸던 결론 둘이 정정됐다: 콘텐츠 뷰 호스트에 입력 주입 이음매가 빠졌다는 것(그것은 offscreen 호스팅의 몫이지 콘텐츠 뷰의 몫이 아니다), 그리고 디자인 표면 플러그인이 지울 만한 군더더기라는 것(그것은 승격 경로의 첫 증명이고, 그 일을 하는 다른 것이 없다).

두 프레임워크가 이제 엔진 소비자를 이름과 **참인 사유**로 떨군다. 그것이 결함이 아니라 설계가 도는 모습이다.

## 코어 표면은 하나, 채우는 방식이 둘 (2026-08-03)

두 프레임워크를 나란히 세우자 마지막 전제가 드러났다. 앱이 여전히 **한 프레임워크의 보상 장치를 자기 것처럼** 들고 있었다.

### 무엇이 잘못됐나

콘텐츠가 사는 자리가 프레임워크마다 다르다. Tauri 에서는 OS 자식 뷰다 — 문서 밖에 살고 메인 웹뷰 앞의 안정된 자식 웹뷰 경계에 고정되며 좌표를 써 줘야 움직인다. Electron 에서는 `<webview>` 태그로 문서 안에 살며 기하 추종 없이 자기 부모를 따라 움직인다.

그 차이를 갚는 Tauri 의 장치 전부 — 홀·스탠드인·레일 클립·네이티브 마우스 브릿지·오버레이 히트테스트 게이트·네이티브로 그리는 골 강조바 — 가 코어에 앉아 **양쪽 모두에서** 돌았다. Electron 에는 갚을 빚이 없으니 그 장치는 멀쩡한 판을 가리고 비우기만 했다. 실측 2026-08-03: 판 활성 전이의 한 프레임에서 브라우저 판 둘이 통째로 비었다.

뿌리는 더 작고 더 나빴다. `domHost` 가 **Tauri 모델을 DOM 에 베껴** 두고 있었다: 모든 `<webview>` 를 전역 층 하나에 달고 `left/top/width/height` 를 써서 밀었다. 그러면 자리와 표면이 두 기준이 되고, 하나는 반드시 늦는다.

### 규칙

> 코어를 통한 표면은 둘 다 동일하다. 코어는 프레임워크 이름도 능력도 묻지 않는다. 분기는 어댑터를 고르는 `src/framework/index.ts` 하나뿐이고 그 뒤로는 없다. 각 프레임워크가 자기 구현·장치·스타일을 그 표면에 건다.

세 번째 프레임워크는 자기 `whale/` 폴더에 자기 것을 쓴다. 코어는 안 바뀌고, 남의 fix 를 물려받지도 않는다.

프레임워크 identity 분기는 **어댑터 선택 한 곳**에서 허용된다. 합성 구현 차이는 capability로
분기하지 않고 어댑터 안에 둔다. 단, 제품이 실제로 기능을 표시하거나 대체해야 하는
`supportsDocumentStart`, `supportsInputInjection`은 공개 capability다. 지킬 수 없는 호출은 선택된
어댑터가 이름을 달고 실패한다.

공개 브라우저 제품 identity는 `soksak-plugin-browser-native` 하나를 유지한다. 장기적으로
`browser-webview` 또는 `browser-embedded`가 제품 의미를 더 정확히 표현할 수 있지만, plugin id는
세션·의존 선언·명령 namespace에 저장되는 identity다. 별도 migration 계약 없이 개명하지 않는다.

자리 선언은 플러그인이 한 번 쓰고 양쪽이 각자 다르게 읽는다: 좌표로 미는 구현에게는 추종 앵커, 문서 안에 사는 구현에게는 **부모**다. 플러그인은 그 차이를 끝내 모른다.

좌표로 미는 쪽의 rect는 중첩된 `data-content-view-body` 요소 자체가 소유한다. 바깥 Tauri
홀 표식은 브라우저 크롬까지 포함하고 어댑터 효과에만 쓰이므로, 그것을 재면 틀린 두 번째
기하가 생긴다. `ProjectSurface` 바깥에서 앱 크롬이 소유하는 배치 축(프로젝트 탭 top/left와
레일 폭)은 커밋 뒤 `layout.reflow`를 발행한다. 따라서 네이티브 bounds는 비전면 창에서
멈출 수 있는 rAF 전달에 의존하지 않는다. 위치 변화는 `layout.reflow`, 크기 변화는
`ResizeObserver`가 Tauri 어댑터를 깨운다. 어댑터는 label별 IPC를 직렬화하고 대기 중 사건을 최신
rect 한 번으로 합친다. Electron 어댑터에는 이 구독과 추종 상태가 전혀 없다.

네이티브 창 resize는 최종 DOM rect가 resize 전과 같아도 권위 에지다. AppKit이 JavaScript 장부 밖에서
child compositor frame을 바꿀 수 있기 때문이다. 따라서 Tauri 어댑터는 유한한 매 창 `resize` 사건에서
현재 슬롯 rect를 같은 직렬 drain으로 강제 적용한다. macOS에서는
`NSWindow.preservesContentDuringLiveResize`도 끈다. 독립적으로 렌더하는 DOM·WKWebView·CEF 표면의
합성에서는 옛 backing 보존이 유효하지 않고 서로 다른 epoch를 늘인 한 프레임으로 만들기 때문이다.
보존을 끄는 것만으로 programmatic `setSize`의 합성이 확정되지는 않는다. 등록된 앱 창의 모든
`NSWindowDidResize` 통지에서 AppKit layout을 끝내고 창 계층을 invalidate한 뒤 그 통지 차례가
끝나기 전에 display한다. 이 하나의 사건 기반 transaction이 가장자리 드래그와 programmatic resize를
함께 덮으며, polling하지 않고 엔진 소유 보조 창에는 적용하지 않는다.
Tauri 프레임워크 어댑터는 tao의 macOS fire-and-forget `setSize`를 공용 `setPhysicalSize` 계약으로
노출하지 않는다. 백엔드 명령이 메인 스레드에서 `setContentSize`·layout·display를 수행하고 그
transaction이 끝난 뒤에만 resolve한다.
Tauri compositor에 등록한 모든 네이티브 surface는 AppKit의 `DuringViewResize` redraw 정책과
`TopLeft` cached-content placement를 쓴다. layer-hosting 기본값 `Never`와
`ScaleAxesIndependently`는 WKWebView/CEF가 다음 프레임을 제출하기 전 마지막 remote-layer 이미지를
새 bounds에 늘인다. `webview.composition.surfaces[]`가 각 live frame과 함께 적용된 두 정책값
(`2`, `11`)을 공개한다.
등록 surface의 autoresizing mask는 `0`이다. 공개 DOM-slot 계약만 그 frame의 주인이다. Tauri
어댑터는 `.space`와 `.tab-body`가 공개한 비율 및 slot의 고정 chrome을 affine 계약으로 저장하고,
`NSWindowDidResize` 통지 안에서 새 viewport에 투영한다. 후행 JS resize 사건은 최종 정착·검증이며
실시간 추종자가 아니다. `webview_bounds`는 계약의 viewport와 현재 native parent viewport가 다른
과거 세대 쓰기를 거부한다. 전체창 engine host 자체의 임의 비례 resize와 폴링은 금지한다. 적용값은
`webview.composition.surfaces[].autoresizingMask`로 공개한다.
windowed Chromium은 각 브라우저마다 전용 AppKit slot host를 가진다. DOM-slot bounds는 이 host에만
적용하고 CEF child는 host 로컬 `(0,0,w,h)`를 채운다. 여러 CEF child를 전체창 host에 직접 붙여
Cocoa 부모 추종과 슬롯 거래가 같은 frame을 함께 소유하는 구조는 금지한다.
`webview.composition.engine.preservesContentDuringLiveResize`가 보존 정책을 공개하며 반드시 `false`여야
한다. Electron은 일반 DOM/창 동작을 유지하고 이 규칙들을 설치하지 않는다.

전이 캡처는 브라우저 marker만 절대 픽셀 크기로 판정하지 않는다. `capture.calibration`은 네이티브
홀이 없는 왼쪽 DOM 레일의 상·중·하에 동일한 40×40 기준자를 멱등하게 노출한다. 기준자는 가장 좁은
레일 안에도 완전히 들어가야 하며 네이티브 표면 아래로 뻗은 기준자는 DOM 보정자로 인정하지 않는다.
선언한 정사각 고유비를 유지한 완전한 DOM 기준자만 CSS 크기로 정규화한다. crop된 조각은 epoch
근거가 아니며 완전한 기준자가 하나도 없는 프레임은 RED다. 먼저 DOM 기준자끼리 한 합성 epoch인지
판정하고 모든 페이지 기준자가 그 epoch와 일치하는지 대조한다. 이 규칙은 clipping을 배율로 오인하지
않으면서 chrome epoch tear와 브라우저만의 blank/stretch를 분리한다. 정착 프레임은 기존 절대 픽셀
크기와 DOM-slot↔viewport 정합도 함께 통과해야 한다.

레일 재배치는 선택적 공개 plugin-view presentation host를 쓴다. Electron은 직접 메인 DOM
플러그인 UI와 일반 DOM 자식 배치를 유지한다. Tauri는 host를 등록하고 같은 plugin provider
source를 pane renderer에 한 번 마운트한 뒤 native member와 하나의 `PaneSurfaceHost` 아래에 둔다.
메인 문서는 renderer가 선언한 node 주소와 frame을 발견용으로 투영할 뿐 플러그인 인스턴스를
복제하지 않는다. 따라서 부모 frame 거래 하나가 보이는 plugin chrome과 document surface를 함께
움직인다.

Pane renderer가 받는 `app` 주소는 메인 renderer의 공개 플러그인 API와 같은 정체성을 유지한다.
특히 `windowLabel()`은 부모 workspace window label을 그대로 답한다. child가 발행한 공개 bus
사건은 그 주소로 main의 command registry와 같은 창 범위에서 합류한다. renderer마다 생기는
모듈 전역은 view 수명이나 command 대상 발견의 경계로 사용할 수 없다.

매니페스트가 선언한 `sidecar` capability도 같은 원칙을 따른다. pane renderer는 부모가 연
불투명 handle 주소만 받고 `open`·`send`·`on`·`close`를 RPC로 사용한다. handle과 이벤트 구독은
presentation 수명에 묶여 pane 종료 시 함께 회수되며, child가 임의 모듈을 직접 적재하지 않는다.

sidecar가 만든 windowed native surface는 `webview.present(label)`로 pane renderer의 선언된
content slot에 결합한다. 새 웹뷰를 만들지 않고 기존 표면을 `PaneSurfaceHost` member로 등록하며,
첫 slot frame이 native에 커밋된 뒤에만 presentation ready를 완료한다.
member 수락 계약은 임의 `NSView`가 아니라 선언된 두 registry, 즉 Tauri child webview
또는 프레임워크 어댑터에 등록된 external native surface 중 하나의 identity를 요구한다.

`webview.composition`은 DOM 앵커·실제 네이티브 frame뿐 아니라 label별 슬롯 rect, 마지막 적용
rect, 가시성, 동기화 대기 상태를 공개한다. 합성 상태를 브라우저 제품 플러그인이
`surface.stats`로 재선언하지 않는다.

포커스 조명의 제품 사실과 장치는 공통 `--dim` 및 콘텐츠 밖 SVG 평면 하나다. 콘텐츠 조상에
`filter`/`opacity`를 적용하지 않고, Tauri와 Electron 어댑터 모두 별도 조명 평면을 설치하지 않는다.
SVG 평면의 mask·base·aperture·cutout·blocked 영역은 모두 `data-node` 주소로 노출한다.

Electron의 `window.snapshot`과 `window.record`는 부모 `webContents.capturePage`의 정규 capturer
수명을 사용한다. 이 수명은 숨었거나 가려진 renderer를 캡처 동안 그리게 하면서 창을 포커스하지
않는다. `stayHidden:true`는 별도 `<webview>` guest surface를 합성 결과에서 제외할 수 있으므로
사용하지 않는다. 프레임 수·간격·파일명은 공통 `windowRecorder`가 소유하고 프레임워크는 한 장의
픽셀만 제공한다.

### `install()` 은 계약 멤버이고, 늦게 가져온다

번들은 하나다 — Electron 도 같은 프론트를 적재한다 — 그래서 두 어댑터가 늘 함께 들어 있다. 적재만으로 걸리게 두면 안 고른 프레임워크의 것도 걸린다. 이미 새고 있었다: `electron.css` 가 Tauri 빌드에도 들어와 있었고, `-webkit-app-region` 이라 무해했을 뿐이다.

그래서 `AppFramework.install()` 을 두고 부팅이 고른 어댑터에 한 번 부른다. `Promise<void>` 이고 자기 코드를 동적 import 로 가져오는데, 이유가 둘이다.

- 어댑터는 **잎**으로 남아야 한다. 거는 쪽은 앱 모듈(플러그인 버스·스토어·DOM)을 만지고 그 모듈들은 다시 프레임워크 문을 본다. 정적으로 물리자 그 순환이 실제로 터졌다: `invoke is not a function` 으로 검사 13벌이 한꺼번에 죽었다.
- 덤으로, 안 고른 프레임워크의 거는 코드는 **받아오지도 않는다.**

부팅이 이것을 기다린다. 안 기다리면 "그 사이에 아무도 안 부른다"는 시간 추측이 되고, 그 추측은 언젠가 틀린다.

스타일도 같은 방식으로 건다 — `styles.css?inline` + `adoptFrameworkStyles(name, css)`. 셀렉터에 프레임워크 이름은 없다: **파일이 곧 조건**이다. 안 걸리면 그 규칙은 애초에 문서에 없다. 이름을 셀렉터에 넣으면 세 번째 프레임워크가 남의 조건을 읽어야 한다.

### `bounds` 는 명령이 아니라 대조다

자리 안에 사는 구현에게 표면은 이미 그 자리를 채우고 있다. 좌표를 다시 쓰면 두 기준이 되살아나므로, `bounds` 는 쓰지 않고 **맞는지 답한다** — 자리와 요청이 다른 것을 가리키면 `false` 다. 조용한 `true` 는 부른 쪽이 옮겼다고 믿는 동안 화면만 다르게 만든다.

자리를 선언하지 않은 뷰는 다른 것이다(오프스크린 추출 뷰) — 요청이 유일한 기하이므로 자기 상자를 들고 산다.

### 공통으로 남은 것

`.hole` 은 뷰의 `transparent` 선언에서 코어가 새긴다 — "이 뷰는 자기 배경을 안 그린다"는 어디서나 같은 뜻이고, 선언이 없는 곳에서 `:not(.hole)` 은 모두를 고른다. `bindPaneUnder` 는 한 함수다 — 들어오는 두 길(콘텐츠 뷰가 포커스를 받았다 / 표면 위의 좌표)이 갈리지 않게.

### 공통이라 부르고 공통이 아니었던 둘 (같은 날 정정)

둘 다 코어에 남아 있었고, 그중 하나는 이 문서에서 공통이라고 **옹호까지** 했다. 둘 다 Electron 의 동작을 바꿨다.

- **`canGlideViews` 가 엔진 미설치를 `false` 로 답했다.** 이 함수가 묻는 것은 *이동하는 표면을 전부 덮을 수 있는가* 이고, 콘텐츠가 문서 안에 살면 덮을 것이 없으므로 전제는 이미 성립이다. `false` 는 "못 덮는다"와 "덮을 게 없다"를 한 값에 담았다. 그 값이 `phase.glide` 로 굳고 → `railTraveling` 이 거짓이 되고 → 배치 전환이 활강 대신 즉시 스냅으로 떨어지며 `beginLayoutMotion` 조차 뜨지 않는다. 전환 하나가 통째로 죽는데 아무것도 실패하지 않는다.
- **`layoutRectMotion` 이 `.hole` 슬롯을 FLIP 보간에서 뺐다.** 주석은 사유가 보편이라고 적었다 — *살아 있는 페이지는 보간 프레임을 못 따라간다*. 아니다: FLIP 은 `transform` 으로 옮기고, 문서 안 게스트는 조상의 transform 을 **합성으로** 같이 탄다(재레이아웃이 아니다). 못 따라갈 일 자체가 없다. 이제 그 제외는 문서 밖 표면을 가진 프레임워크가 건다(`registerRectMotionExclusion`) — 코어는 홀이 무엇인지 모른다. 안 고쳤으면 브라우저 판만 혼자 즉시 도착하고 이웃은 미끄러진다.

그 제외를 "축에 걸지 마라"로 못 박았던 옛 기준은 2026-08-02 실측에 서 있었다 — 문서 안 게스트가 보간 끝에 옛 픽셀을 남겼다는. **그 근거가 사라졌다**: 그때 게스트는 전역 층에 달려 좌표로 밀리고 있었다. 지금은 자기 자리의 자식이다.

- **DOM 구현의 숨김은 평범한 `visibility` 다.** 오프스크린 파킹(`translateX(-200vw)` + `content-visibility`)은 문서 밖 표면이 별도 합성 레이어라 `visibility:hidden` 으로 안 빠지기 때문에 있다. 문서 안 게스트로 재 보니(`scripts/electron/guest-under-effects.test.mjs`) `visibility:hidden` 하나로 사라졌다(중앙 픽셀 234 → 0). `display:none` 은 여전히 거절한다 — 상자를 잃으면 게스트가 0×0 뷰포트로 돌아온다.
- **보이는 하위 층은 `visibility:visible` 을 선언하지 않는다.** 프로젝트→스페이스→탭은 중첩된 파킹 계약이다. CSS `visibility`는 hidden 조상 아래에서도 자식이 `visible`을 직접 선언하면 다시 드러날 수 있으므로, 보임은 속성을 비워 상속하고 숨김만 `hidden`을 선언한다. `webview.surfaces.contentViews.dom`은 각 DOM 콘텐츠 표면의 직접/계산 가시성, 프로젝트 활성성, 슬롯 label과 rect를 공개해 이 합성을 밖에서 대조할 수 있게 한다.

### 게이트

- `frameworkSeam.test.ts` 가 이제 코어에서 문서 밖 표면을 전제하는 장치 이름(`webview_dom_holes`·`webview_overlay_active`·`webview_divider_highlight`·`webview_resize_gesture`·`native-mouse*`)을 부르면, 그리고 코어 스타일시트가 홀을 그리면 실패한다. 둘 다 위반을 심어 확인했다. `plugin:webview-capture|*` 는 **일부러 넣지 않았다** — 두 프레임워크가 다 답하는 공통 능력이고, 이름만 한쪽 플러그인 문법을 닮았을 뿐이다. 그 이름은 어휘의 빚이지 장치 누수가 아니다.
- 벤더 스캔은 상대 경로를 건너뛴다. 우리 폴더 이름이 `electron` 이라, 안 그러면 게이트가 자기 집을 벤더로 신고한다.
- `scripts/e2e/transition-blank-scan.mjs` 는 전이를 걸음마다 정지시키고, 걸음마다 각 판에게 **자기** rect 를 물어 그 자리를 자른다. 고정 사각형은 못 쓴다: 전이 중 판은 움직이므로 옛 rect 는 판 사이를 재고 그것이 "판이 비었다"로 읽힌다 — 그 착시 때문에 한 번은 아직 안 고쳐진 줄 알았다. 판정은 판마다 자기 정지값과의 비교다. 절대 문턱으로는 내용이 적은 터미널(정지 7.3)과 진짜로 비어 버린 브라우저 판(3.7)을 가를 수 없기 때문이다. 기준선은 두 번 재서 붙어 있어야 쓰고, 아직 적재 중인 판은 세지 않으며 그 사실을 감추지 않고 찍는다.

### 전제하지 말고 게스트를 재라

`scripts/electron/guest-under-effects.test.mjs` 가 이 리팩토링이 딛고 선 세 질문을 프레임 단위로 답한다.

- **조상 `filter` 는 Electron 게스트에는 닿지만 WebGL 터미널의 글리프 합성을 깨뜨린다.** 따라서
  `filter`는 공통 조명 장치가 될 수 없다. 문서 안 콘텐츠는 콘텐츠 트리 밖의 단일 SVG 평면이
  어둡게 하고, 문서 밖 Tauri surface만 Tauri 어댑터의 AppKit 조명 평면이 같은 값을 투영한다.
- **`visibility:hidden` 하나로 게스트가 사라진다.** 문서 안에서는 오프스크린 파킹이 필요 없다.
- **파킹에서 돌아올 때 빈 프레임이 없다.** 이걸 읽는 데 주의가 필요했다: 프레임 구독은 현재 프레임을 먼저 배달하므로, 해동 **전** 프레임이 빈 프레임처럼 읽힌다. 그래서 페이지에 박동(정지 상태에서도 프레임이 흐르게)과 표식(해동과 같은 스크립트에서 켠다)을 두어, 게스트를 보일 수 있는 첫 프레임을 추측이 아니라 특정한다. 그렇게 재면 파킹 변형 넷(전체·`visibility`·`transform`·`content-visibility`) 모두 첫 프레임부터 그려져 있다.

전체로 증명된 것: 모든 콘텐츠 표면이 자기가 선언한 자리 안에 있고(`detached: 0`), 전이 중간을 정지시킨 프레임에서 모든 판이 그려져 있으며, DOM 쪽에서 배치 전환이 다시 활강하고, 감사 명령이 네이티브 목록 대신 호스트에게 묻는다 — 그 전에는 거기서 `actual: []` 를 보고해 유령 판정이 빈 집합에서 나왔고, 그러니 언제나 "유령 없음"이었다.
